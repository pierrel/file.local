#+title: v0.0.1-alpha implementation state
#+date: 2026-07-14
#+status: implementation review

* Implemented

- Rust =flocal= binary with =init=, peer pairing/listing, =sync=, =status=,
  conflict inspection/restoration, foreground =watch=, and the private protocol
  responder.
- SSH transport using a fixed validated remote executable and framed standard
  input/output protocol. Share paths travel inside protocol messages.
- SQLite state in WAL/FULL mode, stable installation/share/peer identities,
  per-share sequences, records, peer binding, initial-sync state, and conflicts.
- Git-compatible nested ignore walking with unconditional =.git= exclusion.
  Newly ignored synchronized paths retain local history but are excluded from
  advertised snapshots, so each peer can keep its own ignored content.
- Streaming capture and transfer through validated, content-addressed BLAKE3
  objects. Snapshot and apply streams are split into bounded protocol frames.
  Missing or corrupt cached objects are requested again and eventually repaired
  by a validated replacement transfer.
- Regular files, executable bits, directories, symlinks, deletions/tombstones,
  initial union, deterministic whole-file LWW, and retained conflict inputs.
- Mandatory initial-sync preview/confirmation and versioned JSON for status,
  plans, peer listing, and conflict inspection.
- Receiver-side ignore evaluation before requesting objects, plus
  capability-relative filesystem mutation that cannot follow a swapped parent
  symlink outside the share.
- Compact per-peer causal history, with deterministic LWW used only when
  neither input is known to descend from the other.
- Protocol-version negotiation, per-share process locking, aggregate session
  bounds, a configurable state budget (=FLOCAL_MAX_STATE_BYTES=), and a
  configurable transfer budget (=FLOCAL_MAX_SESSION_BYTES=); both default to
  10 GiB. Sessions also have a configurable duration
  (=FLOCAL_MAX_SESSION_SECONDS=, one hour by default). Files remain streaming
  and have no fixed protocol-level size limit, but receiving installations must
  provision large enough budgets and duration.
- Synchronization operations within one installation are serialized by a
  fail-fast installation lock. This keeps object publication, record commit,
  and pruning in one local critical section for the two-peer alpha.
- Successful two-sided application prunes content objects that are no longer
  referenced by any current record, retained conflict, or pending install.
- Linux and macOS CI for formatting, Clippy, and tests.

* Alpha limitations found during implementation

- The foreground watcher keeps one SSH session open and uses native
  notifications on both peers for prompt saves. Each change-driven round still
  performs a complete scan, and a 15-minute same-session safety audit bounds
  silently missed notifications. Incremental dirty-path scans and the design's
  final operation/version-vector exchange remain deferred.
- Filesystem installation uses destination-local temporaries, fsync, atomic
  exchange/no-replace operations, displaced-entry verification/rollback, and a
  durable install intent replayed on startup. Directory fsync coverage and
  fault-injection across every crash boundary remain incomplete; this alpha
  does not yet claim the detailed design's full crash-consistency guarantee.
- Filesystem mutation is descriptor-relative through a directory capability.
  Additional adversarial stress tests for concurrent symlink swapping remain
  useful acceptance coverage.
- General ACL and extended-attribute preservation is not implemented. New files
  use private transfer permissions plus the synchronized executable bit;
  replacements retain the displaced file's ordinary permission bits.
- Conflict recovery is intentionally narrower than the final design:
  =restore --version winner|loser --to DEST= is available, while peer-named
  inputs and =--base=/=--merged= await three-way merge support. Conflict
  inspection currently uses =conflicts list PATH= and =conflicts show PATH ID=.
- Conflict pruning, connector migration, background
  services, three-way text merge, and ambiguous offline rename inference are
  deferred.
- Offline deletions discovered without a running watcher have no trustworthy
  deletion timestamp; the discovery scan time orders delete-versus-edit in
  this alpha. A running watcher can remove this ambiguity in a later milestone.
- Real macOS filesystem acceptance still needs to be run. The Linux half of
  cross-machine SSH acceptance is now exercised by the =tests/e2e=
  two-container Docker harness over real SSH; seven of its scenarios pin
  known-broken =main= behavior as strict expected failures until the fixes
  land (see [[file:2026-07-16-e2e-harness-design.org][the e2e harness design]]).

These limitations are deliberately stated rather than weakening the detailed
design. Local review decides which are blockers for publishing the alpha and
which may remain visible proof-stage constraints.

The =.flocal-tmp-= filename prefix is reserved at every directory level. Scan
always excludes that namespace so an interrupted staging file cannot enter the
replicated model while recovery rotates to a fresh temporary and retries.

* Validation

- Unit coverage for trusted-type deserialization, path and object-hash
  rejection, =.gitignore= behavior, protocol frame bounds, causal
  reconciliation, convergence, and symlink-parent rejection.
- Integration coverage for scan/apply/delete, nested deletion, file/directory
  transitions, ignored-file preservation and advertisement exclusion, and
  bidirectional synchronization
  across an SSH process boundary using two state stores and directory roots.
- Unit coverage for corrupt-object detection and eventual repair.
- An end-to-end acceptance layer (=make e2e=; a Linux-only CI job) runs
  sixteen first-slice scenarios between two Docker containers over real
  SSH: nine pass on =main= and seven are strict expected-failure pins of
  known =main= bugs, promoted by the pull requests that fix them (see
  [[file:2026-07-16-e2e-harness-design.org][the e2e harness design]]).
- Required local gate: =make check=. It runs formatting and lint checks, the
  complete test suite under coverage, and requires at least 90% line coverage
  both project-wide and on executable lines changed from =github/main=.

* Update 2026-07-18: tombstone retention

The tombstone-retention fix (=agent/tombstone-retention=) merged after this
document was written and corrected several statements above.

What was wrong above:

- The Implemented claim "deletions/tombstones ... work" was inaccurate: a
  persisted tombstone was dropped one scan after its creation, so a peer
  unreachable for a single watch cycle after a deletion never received it
  and its old record resurrected the deleted path on reconnection. The
  end-to-end harness additionally showed the deleting peer's own apply
  recreated deleted parent directories, and that a file-to-directory
  transition failed the connector's whole sync with "apply stopped ...
  File exists" — both self-apply paths the integration coverage listed
  above never drove.
- The Validation list above did not include deletion-retention coverage;
  the harness limitation note ("seven of its scenarios pin known-broken
  =main= behavior") described the pre-fix state.

Current behavior after the fix:

- Tombstone records are retained indefinitely across scans, so an
  unreachable peer cannot resurrect a deleted path. Applying a retained
  tombstone never touches the filesystem, and a received tombstone for a
  path this peer never recorded is not persisted, so a peer cannot pollute
  local state with fabricated deletions. =status= excludes tombstones from
  its entry count and reports the retained count separately (status JSON
  schema 2).
- The design's acknowledgment-based tombstone pruning remains deferred:
  tombstones are never removed in this alpha, deleted path names remain
  visible in state and snapshots for as long as they are retained, and
  retained tombstones count against the session record and metadata
  limits, so a share whose live entries and retained tombstones together
  approach the session record limit (one million) stops synchronizing
  until pruning exists.
- Validation now also covers offline deletion retention across
  disconnected scan cycles with steady-state rounds and recreation over a
  retained tombstone, and rejection of foreign tombstones for
  never-recorded paths (unit and integration), while six of the seven
  end-to-end pins were promoted to plain passing scenarios; the one
  remaining pin is the =bound_peer= error-contract fix.

* Update 2026-07-18: unknown-share sync rejection

A responder asked to synchronize a share it never registered died with an
internal database error before writing any protocol frame, so the connector
saw only a generic connection failure; the "peer identity mismatch"
rejection described by the detailed design was unreachable for that case.
=State::bound_peer= now treats the missing registration as no binding and
the responder answers with the graceful rejection. The end-to-end
peer-identity scenario was promoted from a known failure, so all sixteen
end-to-end scenarios now pass against this tree.
