#+title: One-shot remote-scan progress design
#+date: 2026-09-08
#+status: accepted

* 1. Outcome and failing scenario

=flocal sync add= must complete an initial synchronization whose responder
needs longer than 30 seconds to scan and capture a large changed tree.  It
must show real remote-scan progress while the work is happening, retain a
finite session bound, and report a real peer failure without claiming that the
connector's own SSH cleanup was the peer's failure.

The observed failure is a responder with roughly 5,000 changed regular files.
It hashes and captures them for more than the connector's 30-second no-byte
read interval before it writes its first snapshot frame.  The connector then
reports =peer protocol read timed out=, kills its SSH child, and appends the
misleading locally-caused =remote exited with ... SIGKILL= diagnostic.  The
relationship may be registered, but the initial plan and managed watch never
start.

This is a one-shot explicit-sync change.  Persistent watch already has its
own versioned, round-bounded protocol and is out of scope.

* 2. User flow and protocol version

1. The connector registers the relationship as today, starts an SSH
   =protocol serve= child, and performs the existing two-endpoint reservation.
2. It prints =flocal: scanning local files= and captures its local snapshot.
   It then prints =flocal: waiting for the remote file scan=, sends
   =ScanRequest=, and reads only the responder's scan-phase output.
3. The responder, which has been waiting after the reservation, immediately
   sends =ScanProgress { entries: 0, bytes_read: 0 }=.  It scans, hashes, and
   captures its root, emitting truthful, rate-limited progress before sending
   the existing =SnapshotChunk= and =SnapshotEnd= sequence.
4. The connector writes a throttled stderr line such as =flocal: remote scan
   in progress: 1372 entries, 84 MiB read= only for a full foreground report.
   It then compares snapshots, presents the initial plan, applies confirmation,
   and only after that successful initial completion prints =Connected= and
   starts the managed watch.

The explicit one-shot protocol advances from version 6 to version 7.  Its
=V1Message= gains exactly these scan-phase frames:

#+begin_src rust
ScanRequest,
ScanPreparing,
ScanProgress { entries: u64, bytes_read: u64 },
#+end_src

Their meaning is guarded by the =InitialMessage::Sync { protocol: 7, ... }=
handshake.  A mixed explicit pair rejects the unknown version with the
existing upgrade-both-peers diagnostic; it never falls back to version 6,
whose responder can again be silent for longer than the bounded read interval.
The persistent-watch protocol remains version 7, despite the coincidental
number, because it is a distinct V2 wire family.

The responder waits for =ScanRequest= under the existing absolute peer-session
deadline. This sequencing is intentional: the connector is already reading
when the responder begins progress output, so a long local scan cannot fill an
SSH stdout window with reverse-direction progress frames. It trades an
initial-round parallel scan for a bounded, observable phase.

At =serve_initial= entry, parse =FLOCAL_MAX_SESSION_SECONDS= exactly as today
(default one hour), snapshot that value into the session limits, and create one
absolute responder deadline. The same =Instant= is threaded through the V1
reservation wire, =ScanRequest= read, every scan-phase progress, error, and
snapshot write, and the final completion write; no reservation, frame, or
progress byte renews it. Deadline
expiry closes the protocol and releases the reservation permits through their
existing RAII drops. This preserves an explicitly configured session limit
rather than silently replacing it with a fixed one-hour limit.

* 3. Interfaces and implementation plan

1. In =src/sync.rs=, increment =SYNC_PROTOCOL_VERSION= and add the three strict
   enum variants. The existing 2-MiB declared frame cap is enforced before
   allocation or deserialization. After the closed message enum identifies a
   scan-control frame, a scan-progress or preparation body is limited to 256 bytes and a
   scan-error body to 4 KiB, and its raw declared length is charged before the
   frame is accepted against a 1,024-frame/64-KiB cumulative budget shared by
   progress, preparation, and a terminal error. Thus whitespace or other JSON padding cannot
   bypass acceptance accounting, while malformed input retains the established
   one-frame 2-MiB decode bound. Add a
   scan-specific snapshot reader rather than weakening =read_snapshot=. Its
   exact grammar is =ScanProgress(0,0) ScanPreparing* ScanProgress* (Error |
   SnapshotChunk* SnapshotEnd)=. The mandatory first frame has exact zero
   counters; later progress follows the monotonic rule below. After the first
   chunk, another progress frame or =Error= is invalid. Thus a bounded =Error=
   is the only terminal scan-failure alternative before any snapshot chunk.
   Unexpected placement or any cap violation remains a protocol error.
2. In =src/main.rs=, create the responder deadline at =serve_initial= entry and
   thread it through every V1 reservation-wire read/write before moving the
   responder's one-shot refresh to after a bounded
   =ScanRequest= read. Send the initial zero-progress frame, run the refresh,
   and write the existing snapshot.  On the connector, send =ScanRequest=
   immediately after local refresh and use the scan-specific reader to render
   progress before plan construction.
3. In =src/scan.rs=, add an internal progress checkpoint to the shared scan
   walk.  It owns elapsed-time throttling and calls a supplied closure at most
   once every five seconds, plus the explicit initial checkpoint.  It reports
   work entries examined and total source bytes read; neither value is an
   estimate of a completed snapshot. Every supported non-ignored root entry
   advances the entry count. =ObjectStoreBudget= advances =bytes_read= for
   every real hash/copy read; both scanner inputs feed one shared throttle.
4. In =src/state.rs=, let only the scan-local =ObjectStoreBudget= capture path
   invoke that checkpoint for each one-MiB hashing and object-copy read.
   Let object collection report each metadata row or stored
   object entry as an opaque =ScanPreparing= pulse so the responder can send
   the mandatory zero before collection without becoming silent during a large
   retry cleanup. The pulse exposes no global count to a share-scoped peer.
   Existing callers keep the simple no-progress method.  The exclusive object
   lock, remaining-capacity accounting, duplicate/source-snapshot checks, and
   temporary-object cleanup do not change.
5. Give scan-phase peer errors a typed path through =Remote=.  A responder
   scan failure is a bounded =Message::Error= rendered as =remote file scan
   failed: ...=.  If the connector itself ends an unresponsive SSH child, the
   user-facing timeout says it stopped receiving remote scan progress; it does
   not append the child's signal-9 status as if that were an independent remote
   failure.
6. Update =README.org= as the current contract: describe the truthful remote
   scan-progress line and scan-failure wording, retain the rule that =Connected=
   follows confirmed initial completion only, and replace its explicit-sync
   version-6/rolling-upgrade statement with version 7 and upgrade-both-peers
   guidance.  No historical dated document changes.

* 4. Failure and security bounds

- The initial =ScanProgress= is exactly =(0, 0)=. Opaque =ScanPreparing= pulses
  may follow while global retry cleanup makes real progress; they carry no
  count and are invalid after the first nonzero scan counter. Later counters are
  componentwise nondecreasing and each later frame must increase at least one
  component. The reader admits at most 1,024 scan-control frames and 64 KiB of
  raw declared control-frame metadata in a scan phase; each accepted progress
  or preparation body is at most 256 bytes and each accepted scan-error body at most 4 KiB.
  The established 2-MiB generic cap remains the pre-deserialization bound.
  These frames reset only the existing no-byte read wait; they never extend
  either endpoint's configured absolute session deadline.
- The existing =MAX_FRAME=, snapshot-record, snapshot-metadata, and
  transfer-byte limits remain in force. A flooding, malformed, out-of-order,
  non-monotonic, or stalled peer fails the protocol rather than gaining an
  unbounded keepalive channel.
- Progress contains only share-root counts, while preparation is an opaque
  activity pulse. It exposes no paths, names, object hashes, global counts,
  roots, share IDs, queue positions, or peer-private scheduling information.
  The frames are accepted only after the existing authenticated binding and
  reservation checks.
- A scan checkpoint cannot interrupt a single blocking filesystem syscall.
  Hash and object-copy reads checkpoint per MiB, but an indefinitely blocked
  directory, metadata, or file read produces no fictitious progress; after 30
  seconds without a byte the connector reports the ordinary remote-scan
  no-progress timeout and tears down the session. The fix does not raise that
  boundary merely to hide an unresponsive filesystem.
- Preparation pulses likewise occur only between completed metadata and object
  work items. Acquiring the object lock, the atomic pending-object deletion,
  loading an install intent or prior-record set, and any individual SQLite call
  remain indivisible operations. If one produces no byte for 30 seconds, that
  is intentionally a no-progress timeout. Splitting these established state
  transactions or emitting a timer heartbeat is outside this observed
  large-root-scan fix; the scaled silent-peer test pins the retained boundary.
- The responder uses its one absolute deadline for reservation, =ScanRequest=,
  and every new scan-phase progress, error, and snapshot write. The existing
  timed reader retains the same total-session and no-byte bounds for later
  input. Bounding every post-snapshot output write is a separate existing
  one-shot transport concern and is not expanded by this scan fix.
- For a remote =Message::Error=, the connector waits for the responder's clean
  exit through a dedicated remote-error finalizer; it returns a bounded,
  terminal-safe rendering of the peer's scan error when exit is clean. A local
  no-progress timeout instead uses a dedicated abort/reap path. Neither path
  calls generic =finish_after_error=, so a connector-caused SIGKILL is never
  appended as a misleading remote-exit failure.
- No filesystem authority changes: scanner no-follow opens, ignore handling,
  root-identity checks, source-change rejection, object verification, and
  capacity admission remain the existing paths.  The callback reports after
  real reads; it cannot alter the file bytes or the budget.

Linux and macOS both use the existing Unix SSH, descriptor, Rustix, and
capability-based scanner paths. No timing behavior depends on Docker:
platform-neutral protocol and scan tests cover the framing and accounting on
macOS, while the existing full Docker suite remains regression validation for
the real SSH product path.

* 5. Fast deterministic fail-to-pass test

The observed 5,000-file, over-30-second responder scan remains the motivating
production scenario. Do not add it, an artificial capture-delay hook, or any
new long Docker scenario to CI: CI has hard time limits and the protocol
boundary can be proved much faster in process.

Factor the existing reader's production limits into a private =ProtocolLimits=
value. It snapshots the configured =FLOCAL_MAX_SESSION_SECONDS= total-session
duration while retaining fixed production values of 30 seconds without a byte
and a five-second scan-progress cadence. Test-only constructors supply shorter
idle and progress intervals with ample scheduler margin, plus an explicit
configured session duration.

The fail-to-pass test uses a real Unix-stream pair and responder thread. It
first demonstrates, against the pre-frame behavior, that a scan held past the
scaled idle interval causes the same timed-read failure. Its final assertion
uses the new scan-control exchange: scripted preparation and progress frames
arrive at bounded intervals before the idle deadline, the total exchange lasts
longer than that deadline, and the snapshot completes. It therefore exercises
framing, flushing, =TimedReader= polling, and the actual timeout boundary
without sleeping for 30 seconds or mocking transport reads.

A separate real temporary-tree scan/accounting test creates regular files,
runs the ordinary capability-based scanner and =ObjectStoreBudget= path with a
test progress callback, and verifies emitted counters are monotonic while
captured objects, source-snapshot checks, and cumulative capacity accounting
retain their existing results. It proves that the callback is attached to real
directory traversal/hash/copy work rather than a synthetic timer.

The final tests also cover version rejection; exact scan grammar (including no
progress after the first snapshot chunk and missing/wrong opening =(0,0)=
progress); raw-length acceptance accounting; padded progress/error frames;
each per-frame cap and the
1,024-frame/64-KiB cumulative caps; componentwise counter regression or a
repeated zero frame; each cumulative frame and byte cap; a one-shot reservation wire whose longer frame deadline is
clamped by the configured session deadline; truthful timeout versus
clean remote-error finalization. Existing sync-add tests retain the invariant
that =Connected= appears only after confirmed initial completion. Run these fast tests
with =make check= and retain the normal complete Docker E2E suite as part of
full validation; there is no focused long-running Docker test.

* 6. Alternatives rejected

- Raising or removing the 30-second no-byte timeout hides a stalled peer and
  leaves the user without a progress boundary.
- A generic heartbeat frame would affect unrelated phases and persistent watch,
  while still allowing the responder to fill an unread SSH window during a
  concurrent local scan.
- Keeping both scans concurrent and merely rate-limiting progress is not a
  proof of liveness: a slow connector scan can stop draining the responder's
  output. The explicit request is the small ordering boundary that makes
  progress deliverable.
- Per-file paths or object identifiers would add noisy output and unnecessary
  remote filesystem disclosure.  Counts are sufficient to show that work is
  advancing.
