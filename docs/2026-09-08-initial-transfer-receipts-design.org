#+title: Initial transfer receipt design
#+date: 2026-09-08
#+status: accepted

* 1. Outcome and reproduced boundary

Make a public =flocal sync add ... --yes= survive a large *connector-to-
responder* initial object transfer when the responder is genuinely receiving
and verifying objects for longer than the connector's 30-second no-byte read
limit.  This is a second explicit one-shot liveness boundary after the already
fixed remote scan boundary; it does not weaken that limit or turn it into a
timer heartbeat.

The committed known failure at =5192794= is the required product
reproduction.  It starts two managed Docker peers, writes 5,000 tiny regular
files only on the connector, and uses the public SSH =sync add= command.  The
connector finishes its scan and the snapshot comparison.  The responder then
asks for the connector objects.  Instrumentation shows the responder has
received 1,000 objects at 4.5 seconds, 2,000 at 10.4, 3,000 at 17.5, and
4,000 at 26.2, but emits no V1 output while consuming the remaining object
frames.  The connector eventually reports:

#+begin_example
peer protocol read timed out; remote exited with Some(ExitStatus(unix_wait_status(9)))
#+end_example

The signal is caused by the connector's cleanup, not an independent responder
failure.  The immediate root cause is directional: after receiving the
responder's =Need=, the connector writes every requested object and only then
begins reading its stdout.  A receiver-side progress frame cannot help unless
the sender deliberately reaches a read boundary during that transfer.

* 2. User flow

1. Initial registration, reservation, local scan, explicit =ScanRequest=,
   responder scan progress, snapshot comparison, plan construction, and
   confirmation retain their current behavior.
2. When the responder's validated plan needs connector objects, it sends its
   existing ordered =Need { hashes }=.  The connector sends those objects in
   bounded batches instead of one unbroken stream.
3. After each complete batch, the connector sends =TransferBatchEnd= and waits
   for the responder's exact cumulative =TransferReceipt { objects, bytes }=.
   The responder emits that receipt only after =receive_object_for_share= has
   finished every object in the batch, including verification and its durable
   receiving/verified state transition.
4. The connector prints a rate-limited foreground line only from an accepted
   receipt, for example =flocal: remote file transfer in progress: 2048
   objects, 2.0 KiB received=.  This says what is known: the remote peer
   reports having received and verified that cumulative amount.  It does not
   claim the initial synchronization or apply is complete.  =Connected=
   remains after confirmed, successful initial completion.
5. After the final receipt, the connector sends the existing =Done= and the
   responder continues the established verification, apply, heads, and commit
   exchange.

The 5,000-file E2E will therefore receive several real responder bytes while
the actual receiver work is in progress, cross the original 30-second total
boundary, and complete with equal trees.

* 3. Protocol and state-flow changes

1. Advance only =SYNC_PROTOCOL_VERSION= from 7 to 8.  Add these V1 messages:

   #+begin_src rust
   TransferBatchEnd,
   TransferReceipt { objects: u64, bytes: u64 },
   #+end_src

   They are valid only in the connector-to-responder object-transfer subphase
   after the responder has issued its post-plan =Need=.  An explicit mixed
   pair rejects version 8 through the current version handshake and tells the
   user to upgrade both peers.  V2 persistent watch remains version 7 and its
   wire family is untouched.

2. In =src/sync.rs=, add one shared, internal batch-boundary helper.  A batch
   contains at most 1,024 objects or 16 MiB of declared validated object size,
   whichever is reached first; an oversized single object forms its own batch.
   The final nonempty remainder is a batch.  The same helper is used by the
   connector sender and responder validator, so a peer cannot choose tiny
   batches to manufacture receipt traffic.  Before its first =ObjectStart=,
   the connector plans the complete ordered request with that helper and
   rejects a request requiring more than 2,048 receipts; the responder
   independently enforces the same count while receiving.

   The responder's ordered =Need= is already the connector's send order.  In
   =serve_sync= replace the unordered post-plan requested-input map with an
   ordered queue of expected =(hash, size)= values.  Each =ObjectStart= must
   match its queue head and the existing size and total-transfer checks still
   run.  The receiver therefore knows exactly when a batch must end.  It
   rejects an early, empty, late, or extra =TransferBatchEnd=, an object after a
   due boundary, a receipt in the wrong direction, and =Done= before the final
   required boundary.  This is a narrow tightening: the existing connector
   already sends the responder's requested hashes in order.

3. In =src/main.rs=, after each connector batch write, read exactly one
   =TransferReceipt= from =Remote.output= before writing another object.  Its
   counters must equal the connector's cumulative batches sent, rather than
   merely be monotonic.  A received =Error= is a peer transfer failure; any
   other V1 message is a protocol error.  A small local receipt-reporter owns
   the five-second stderr cadence and never alters protocol cadence or state.

4. In responder =serve_sync=, retain cumulative received-object and byte
   counters beside the existing transfer-limit accounting.  A valid batch end
   writes exactly one cumulative receipt, resets only the batch-local counters,
   and then resumes reading.  It does not scan, hash, or synthesize a timer
   event.  The branch which serves objects to the connector is unchanged: the
   connector is already reading continuously while receiving that direction.

5. The new receiver receipt path uses a dedicated =Remote= local-timeout
   finalizer, parallel to the scan-timeout path.  If its timed read expires,
   it kills and reaps SSH but returns only =stopped receiving remote file
   transfer progress before the peer protocol deadline= (plus bounded remote
   stderr if any).  It must not route through =finish_after_error= or append
   the connector-caused SIGKILL status.  A clean, bounded peer =Error= retains
   its peer-error wording.

* 4. Bounded hostile-peer behavior and failure modes

- The existing 2-MiB pre-decode frame cap remains.  A decoded
  =TransferBatchEnd= or =TransferReceipt= body is capped at 256 raw declared
  bytes.  The connector accepts at most 2,048 receipts per one-shot session;
  the responder enforces the same cap before writing another receipt.  With the default 10-GiB
  transfer limit, 1,024-object and 16-MiB boundaries require at most 1,617
  batches (977 count-driven plus 640 byte-driven), so valid default-limit work
  remains below the cap.  A locally configured larger transfer allowance does
  not silently create an unlimited keepalive channel: a session needing more
  receipts fails clearly before exceeding the fixed control-frame cap.
- Every receipt is caused by a connector-supplied, validated batch boundary;
  the responder cannot send unsolicited receipts and the connector cannot
  cause one per object.  The connector validates exact cumulative counters and
  the phase grammar.  Counters disclose only a total object count and bytes,
  never paths, names, hashes, root names, or state outside the share.
- Receipts refresh the same 30-second no-byte read wait but never the absolute
  =FLOCAL_MAX_SESSION_SECONDS= deadline or the existing transfer, metadata,
  record, authorization, object-hash, no-follow, capacity, and source-snapshot
  limits.  A silent receiver, malformed frame, wrong count, early/late batch
  marker, duplicate request, or oversized receipt fails rather than retaining
  a live session.
- The responder's existing generic post-snapshot output writer is not
  redesigned here.  The new receipt is sent only after a boundary at which the
  connector is waiting and drains it, so it adds no unsolicited output stream
  or output-window flood.  A peer that stops reading can already block an
  existing one-shot response write; making every legacy writer deadline-aware
  remains a separate transport change.
- A single blocked object read, SQLite operation, or filesystem apply can
  still produce no receipt for 30 seconds.  That is intentionally a timeout,
  not a fictitious progress message.  In particular, after the final =Done=
  the responder's existing apply phase can still be silent.  This design adds
  no apply frame or heartbeat unless the promoted natural 5,000-file test
  demonstrates that apply, rather than object receipt, is the remaining
  observed boundary.

Linux and macOS use the same Rust V1 framing, Unix SSH child, timed reader,
and capability-based object storage code.  Docker is Linux-only test
infrastructure; the protocol grammar, receipt cap, batching, timeout cleanup,
and object-state tests run on both supported platforms.

* 5. Acceptance and fail-to-pass validation

1. Strengthen the committed known failure before implementation.  Give the
   harness's expected-failure wrapper a narrow expected-error predicate (its
   current unrestricted form cannot distinguish this timeout from an unrelated
   failure).  The 5,000-file scenario must cross 30 seconds and match both
   =peer protocol read timed out= and the current cleanup suffix.  Any other
   error, an outer 5-minute target timeout, or a fast result fails the pin.
2. Implement version 8, promote that identical Docker scenario by removing
   =known_failure=, retain its five-minute external safety deadline, and assert
   successful =sync add=, elapsed time above 30 seconds, at least three
   =remote file transfer in progress= lines, and equal trees.  It must not use
   an artificial delay, a test-only wire frame, a raised product timeout, or a
   background-daemon shortcut.
3. Add fast V1 unit tests for version-8 round trips and mixed-version
   rejection; valid one-object, count-boundary, byte-boundary, oversized-single
   object, and final-short batch grammars; empty/early/late/extra batch ends;
   out-of-order/duplicate objects; unsolicited, malformed, padded, oversized,
   over-cap, and counter-mismatching receipts; exact request-order validation;
   and transfer/session-limit interaction.
4. Add a real Unix-stream timed-reader test which sends a receipt below the
   scaled idle deadline, lasts beyond that deadline over multiple batches, and
   succeeds; pair it with a silent receiver test that returns the truthful
   transfer-progress timeout and verifies no locally-caused exit-status suffix.
   Keep the existing scan-progress timeout test unchanged.
5. Run the focused promoted Docker scenario, normal =make e2e= selection,
   =make check= (including whole-project and changed-line coverage), formatting
   and Clippy, Linux CI Docker coverage, and macOS native tests.  Update
   =README.org= in the implementation change to name explicit protocol 8,
   upgrade-both-peers behavior, the transfer-progress line, and the truthful
   local timeout.  Do not change dated historical documents.

* 6. Alternatives rejected

- Raising or removing the 30-second idle limit would hide a stalled receiver
  and leave a hung initial sync without a truthful boundary.
- A responder timer heartbeat or unbounded receiver progress stream would let
  a hostile peer refresh the read timeout without completing an object.  It
  also fails to solve the connector's current write-all-then-read ordering.
- A reader thread while the connector writes would add child ownership,
  channel, cancellation, and error-race machinery.  The existing one-shot
  protocol is naturally turn-based; bounded batch receipts establish the
  needed read boundary with no concurrent SSH access.
- Adding apply progress now would conflate a possible later silent phase with
  the measured object-consumption failure.  The promoted natural test decides
  whether that separate work is needed.
- A larger fixture, artificial sleep, or a test-only protocol frame would not
  prove the observed receiver backpressure and would add avoidable CI time or
  production surface.
