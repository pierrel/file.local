#+title: Initial transfer receipt design
#+date: 2026-09-08
#+status: accepted

* 1. Outcome and reproduced boundary

Make a public =flocal sync add ... --yes= survive a large *connector-to-
responder* initial transfer when the responder is genuinely receiving objects
and applying them for longer than the connector's 30-second no-byte read
limit.  This is a second explicit one-shot liveness boundary after the already
fixed remote scan boundary; it does not weaken that limit or turn it into a
timer heartbeat.

The committed known failure at =5192794= is the required product
reproduction.  It starts two managed Docker peers, writes 5,000 tiny regular
files only on the connector, and uses the public SSH =sync add= command.  The
connector finishes its scan and the snapshot comparison.  The responder then
asks for the connector objects.  Instrumentation shows the responder has
received 1,000 objects at 4.5 seconds, 2,000 at 10.4, 3,000 at 17.5, and
4,000 at 26.2, but emits no V1 output while consuming the remaining object
frames.  The connector eventually reports:

#+begin_example
peer protocol read timed out; remote exited with Some(ExitStatus(unix_wait_status(9)))
#+end_example

The signal is caused by the connector's cleanup, not an independent responder
failure.  The immediate root cause is directional: after receiving the
responder's =Need=, the connector writes every requested object and only then
begins reading its stdout.  A receiver-side progress frame cannot help unless
the sender deliberately reaches a read boundary during that transfer.

A detached diagnostic reran the same case with the connector idle limit raised
from 30 to 120 seconds.  The responder finished receiving all 5,000 objects at
36.45 seconds, then entered =apply_complete_plan=.  It was still applying when
the connector's 120-second read-idle timeout killed it.  The responder tree
contained about 2,838 of 5,000 files and its durable =pending_install= remained
true.  Apply silence is therefore measured behavior in this exact scenario,
not a speculative extension of the transfer fix.

* 2. User flow

1. Initial registration, reservation, local scan, explicit =ScanRequest=,
   responder scan progress, snapshot comparison, plan construction, and
   confirmation retain their current behavior.
2. When the responder's validated plan needs connector objects, it sends its
   existing ordered =Need { hashes }=.  The connector sends those objects in
   bounded batches instead of one unbroken stream.
3. Each nonempty batch is one fixed, bounded phase: the connector sends every
   object and =TransferBatchEnd=, then waits for the responder's exact
   cumulative =TransferReceipt { objects, bytes }=.  The responder emits that
   receipt only after =receive_object_for_share= has finished every object in
   the batch, including verification and its durable receiving/verified state
   transition.  A peer which stops reading therefore has the same truthful
   phase deadline as a peer which stops replying.
4. The connector prints a rate-limited foreground line only from an accepted
   receipt, for example =flocal: remote file transfer in progress: 2048
   objects, 2.0 KiB received=.  This says what is known: the remote peer
   reports having received and verified that cumulative amount.  It does not
   claim the initial synchronization or apply is complete.  =Connected=
   remains after confirmed, successful initial completion.
5. After the final receipt, the connector sends the existing =Done= and the
   responder verifies the plan and starts its existing durable apply loop.
   After each real record becomes visible and durable, it emits a bounded
   =ApplyProgress { records }= frame.  It emits no frame merely because time
   passed or because an install intent exists.
6. The connector renders accepted apply progress as =flocal: remote apply in
   progress: 2838 records completed=.  Only the existing =HeadChunk=,
   =Applied=, and commit exchange establish completion.  =Connected= remains
   after confirmed, successful initial completion.
7. After the responder has sent =Applied=, the connector performs its own
   existing durable local apply before it can send acknowledged heads and
   =CommitAck=.  It emits the same bounded real =ApplyProgress { records }=
   frames from that apply callback.  The responder drains and validates them
   while waiting for heads, and the connector renders =flocal: local apply in
   progress: 2838 records completed=.  These lines mean that local records are
   already durable; they do not claim the final acknowledgement or initial
   synchronization is complete.

The 5,000-file E2E will therefore exchange several real responder and
connector bytes while each actual apply is in progress, cross the original
30-second total boundary in both directions, and complete with equal trees.

* 3. Protocol and state-flow changes

1. Advance only =SYNC_PROTOCOL_VERSION= from 7 to 8.  Add these V1 messages:

   #+begin_src rust
   TransferBatchEnd,
   TransferReceipt { objects: u64, bytes: u64 },
   ApplyProgress { records: u64 },
   #+end_src

   =TransferBatchEnd= and =TransferReceipt= are valid only in the
   connector-to-responder object-transfer subphase after the responder has
   issued its post-plan =Need=.  =ApplyProgress= is valid in exactly two
   direction-specific apply windows: responder-to-connector after the
   connector's final =Done= and before the responder's =HeadChunk=/=Applied=
   terminal response, and connector-to-responder after that =Applied= while
   the responder waits for =HeadChunk=/=CommitAck=.  An explicit mixed pair
   rejects version 8 through the current version handshake and tells the user
   to upgrade both peers. V2 persistent watch remains version 7 and its wire
   family is untouched.

2. Keep batch policy private to =src/main.rs=: both the connector sender and
   =serve_sync= receiver already live there.  One private
   =transfer_batch_ends= helper consumes the ordered validated =(hash, size)=
   request and returns its batch boundaries; the connector tracks expected
   cumulative object and byte totals while traversing those boundaries.  A
   batch contains at most
   1,024 objects or 16 MiB of declared validated object size, whichever is
   reached first; an oversized single object forms its own batch, and the
   final nonempty remainder is a batch.  The connector plans that same
   ordered request before its first =ObjectStart= and rejects more than 2,048
   receipts; the responder independently advances the same state while
   receiving.  It is not a public =sync.rs= API.

   The responder's ordered =Need= is already the connector's send order.  In
   =serve_sync= replace the unordered post-plan requested-input map with an
   ordered queue of expected =(hash, size)= values.  Each =ObjectStart= must
   match its queue head and the existing size and total-transfer checks still
   run.  The receiver therefore knows exactly when a batch must end.  It
   rejects an early, empty, late, or extra =TransferBatchEnd=, an object after
   a due boundary, a receipt in the wrong direction, and =Done= before the
   final required boundary.  An explicit empty =Need= has no batches and no
   receipts: the connector writes =Done= immediately and the responder
   accepts only that transition before verification/apply.  This is a narrow
   tightening: the existing connector already sends the responder's requested
   hashes in order.

3. In =src/main.rs=, every nonempty batch gets one deadline at its first
   =ObjectStart=: =min(session_deadline, now + 30 seconds)=.  Add the narrow
   public =sync::send_object_until(state, hash, writer: &impl AsFd, deadline)=
   for the existing verified-object framing only.  It sends every
   =ObjectStart=, =ObjectChunk=, and =ObjectEnd= through the existing
   descriptor-aware =write_v1_message_until=; =main.rs= sends
   =TransferBatchEnd= by the same writer and same unchanged deadline.  It then
   reads exactly one receipt with a new narrowly exposed
   =read_v1_message_until_with_len(reader, deadline)= using that unchanged
   deadline before writing another object.  No chunk, partial write, partial
   read, or receipt renews this deadline.  Thus a silent or deliberately
   trickle-reading responder cannot keep the connector blocked in
   =send_object= indefinitely before a receipt boundary.

   The receipt counters must equal the connector's cumulative batches sent,
   rather than merely be monotonic.  A received =Error= is a peer transfer
   failure; any other V1 message is a protocol error.  A small local
   receipt-reporter owns the five-second stderr cadence and never alters
   protocol cadence or state.

4. In responder =serve_sync=, retain cumulative received-object and byte
   counters beside the existing transfer-limit accounting.  A valid batch end
   writes exactly one cumulative receipt through the descriptor-aware writer
   with =min(session_deadline, now + 30 seconds)=, removes that expected batch
   endpoint, and then resumes reading.  A connector which stops draining
   receipts therefore cannot hold the responder indefinitely.  The responder
   does not scan, hash, or synthesize a timer event.  Expose only the two V1
   length-returning decoders required for this:
   =read_v1_message_with_len(reader)= for ordinary =Read= callers and
   =read_v1_message_until_with_len(reader, deadline)= for descriptor/deadline
   callers.  Each applies the existing 2-MiB pre-decode frame ceiling, then
   returns =(message, declared_body_bytes)= so its caller applies the cap for
   the decoded variant.  JSON padding is therefore visible and rejected even
   though the tagged V1 enum cannot choose a variant-specific raw limit before
   decoding.  In this receipt-only phase, =TransferBatchEnd= and
   =TransferReceipt= are at most 256 declared bytes; a peer =Error= is allowed
   only up to the separately bounded 4-KiB one-shot-error encoding.  The branch
   which serves objects to the connector is unchanged: the connector is already
   reading continuously while receiving that direction.

5. In =src/sync.rs=, thread one small completion callback through the existing
   =apply_complete_plan_with_root_skipping_inner=.  The ordinary public
   =apply_complete_plan_with_progress(..., callback)= and new managed
   =apply_complete_plan_and_enable_managed_with_progress(..., generation,
   callback)= are thin wrappers over that one inner operation; their existing
   no-progress counterparts pass a no-op.  This avoids two apply loops and
   gives both initial modes the identical ordering.  Invoke the callback only
   after =apply_record= succeeds, =sync_applied_record= has made that path
   durable, and the record has entered the existing =completed= recovery
   baseline.  Its argument is that completed record count.  It is not called
   for a skipped echo/tombstone, an ignored record, a failed record, or an
   invalidated record.

   The durable install intent stays in place until the existing final
   =finish_install= transaction.  A callback failure is wrapped in the narrow
   =sync::ApplyProgressWriteError=.  On the responder, =serve_sync= recognizes
   that type and returns it directly, without attempting its ordinary
   apply-failure =Message::Error= write on the already failed output.  On the
   connector, the same type aborts the remote session without writing heads or
   =CommitAck=.  The already durable paths and intent after either failure are
   recovered by the established interrupted-install path, exactly as on a
   process crash.  For a managed initial apply, a callback failure occurs
   before the shared inner operation publishes its managed queue request:
   there is no enabled-generation handoff or daemon start, and the retained
   generation-bound install intent is the one recovered later.  Ordinary apply
   errors retain the existing peer =Error= path.  If =ApplyInvalidated= occurs,
   its existing recovery uses the same completed baseline; no success frame is
   emitted for the invalidated record and no terminal success follows it.

   =serve_initial= takes a shared =output: &impl AsFd=.  It makes one
   =DirectWriter(output)= for ordinary sequential =serve_sync= output and a
   private =ServeSyncProgress= containing two narrow callbacks.  The receipt
   callback calls =write_v1_message_until= with its fixed 30-second deadline;
   the responder apply callback calls the same primitive with the absolute
   session deadline.  It passes the writer and callback pair to =serve_sync=.
   The connector's matching apply callback writes to =Remote.input= through
   the same deadline-aware primitive.  No unsafe raw descriptor, =RefCell=, or
   overlapping mutable borrow is needed; calls are sequential and each output
   uses one capability.  Direct =serve_sync= Vec unit callers use no-op receipt
   callbacks and a no-op or test apply closure, and need no descriptor
   abstraction.

6. On the connector, extend the existing post-=Done= read loop to accept only
   strictly increasing, nonzero responder =ApplyProgress.records= values before
   the existing terminal response.  Each value is at most the validated plan's
   record count.  Its post-=Done= grammar is
   =ApplyProgress* (Error | HeadChunk* Applied)=, with progress forbidden after
   the first head.  Each loop read first uses the 2-MiB global ceiling and
   returns the declared body size; it then permits =ApplyProgress= and
   =Applied= only up to 256 bytes, =Error= only up to the bounded 4-KiB
   one-shot-error encoding, and =HeadChunk= up to the existing =MAX_FRAME=.
   A head chunk is still checked against the existing per-frame record shape,
   cumulative =MAX_RECORDS_PER_SESSION=, and metadata-byte limits before it is
   retained.  This keeps a valid five-thousand-record terminal manifest legal
   while detecting padding after decode.  At most 1,024 apply-progress frames
   are accepted.  A local five-second logger may suppress display while it
   still validates and drains every frame, so accepted frames cannot flood
   foreground output; they do not mutate local records or acknowledge heads.

7. After it receives =Applied=, the connector invokes the matching ordinary or
   managed progress wrapper while it applies its own plan.  Its callback uses
   the same five-second reporting cadence, emits at most 1,024 strictly
   increasing nonzero values, and writes each frame through
   =write_v1_message_until(Remote.input, ..., session_deadline)=.  The
   responder's final commit grammar becomes
   =ApplyProgress* HeadChunk* CommitAck=, with progress forbidden after the
   first head.  It drains frames through its =TimedReader=, rejects an
   out-of-range, repeated, regressing, padded, over-cap, or misplaced progress
   frame, and applies the same 256-byte decoded-variant control bound and
   1,024-frame cap.  The connector's foreground reporter uses the same
   five-second cadence but writes the truthful =local apply in progress: N
   records completed= line only for frames it has successfully written.

   No artificial progress is sent while an individual local record, SQLite
   operation, or final managed transaction blocks.  If the responder ceases
   reading, a typed deadline source within =ApplyProgressWriteError= selects
   connector local-apply timeout cleanup; an =EPIPE= or other write cause is
   reported as that actual cause after bounded abort/reap.  Conversely, a
   silent connector local apply leaves the responder's existing 30-second
   =TimedReader= to close the session; the later connector write then reports
   its real failure.  Neither path sends heads, =CommitAck=, or =Connected=.

8. Make deadline expiry typed at the framing boundary.  The descriptor-aware
   read/write helpers return a narrow =sync::ProtocolDeadlineExpired= only
   when their fixed deadline actually expires; they preserve an OS write error
   such as =EPIPE=, an object-read error, or malformed JSON as its original
   error.  A phase-aware =Remote= helper recognizes only that typed error,
   either directly or as the typed source of =ApplyProgressWriteError=. It kills
   and reaps SSH, then reports =stopped sending or receiving remote
   file-transfer batch progress before the peer protocol deadline= for a
   transfer-batch expiry, =stopped receiving remote apply progress before the
   peer protocol deadline= for a responder-apply read expiry, or =stopped
   sending local apply progress before the peer protocol deadline= for a
   connector callback expiry.  The final responder =Done= also has one fixed
   =min(session_deadline, now + 30 seconds)= read deadline; its expiry reports
   =stopped receiving final synchronization confirmation before the peer
   protocol deadline=.  It may append bounded remote stderr, but none of these
   routes goes through =finish_after_error= or appends the connector-caused
   SIGKILL status.  There is no string matching or elapsed-time inference.  A
   clean, bounded peer =Error= retains its peer-error wording.

* 4. Bounded hostile-peer behavior and failure modes

- The existing 2-MiB =MAX_FRAME= ceiling is the only pre-decode bound for this
  tagged V1 enum.  The narrowly exposed length-returning decoders report the
  raw declared body length alongside the decoded message, so JSON padding is
  rejected by the receiver's decoded-variant limit rather than overlooked.
  =TransferBatchEnd=, =TransferReceipt=, =ApplyProgress=, and =Applied= are
  each limited to 256 bytes; every version-8 one-shot =Error= is serialized
  through a byte-safe 4-KiB truncator and the receiver enforces that 4-KiB
  declared-length limit.  Unexpected or oversized decoded messages are named
  only by phase and declared length, never debug-formatted, so an attacker
  cannot copy a payload into operator diagnostics.  =HeadChunk= retains
  =MAX_FRAME=, its established record-shape bound, cumulative
  =MAX_RECORDS_PER_SESSION=, and metadata-byte accounting.  The connector
  accepts at most 2,048 receipts and each side
  accepts at most 1,024 apply-progress frames in its own direction; a sender
  enforces its report cap before writing another frame.  With the default
  10-GiB transfer limit, 1,024-object and 16-MiB boundaries require at most
  1,617 batches (977 count-driven plus 640 byte-driven), so valid
  default-limit work remains below the cap.  A locally configured larger
  transfer allowance does not silently create an unlimited keepalive channel:
  a session needing more receipts fails clearly before exceeding the fixed
  control-frame cap.
- Every receipt is caused by a connector-supplied, validated batch boundary;
  the responder cannot send unsolicited receipts and the connector cannot
  cause one per object.  The connector validates exact cumulative counters and
  the phase grammar.  Receipt and apply counters disclose only total object
  counts and bytes, never paths, names, hashes, root names, or state outside
  the share.
- Each receipt and either direction's completed-record frame refreshes the
  established 30-second no-byte read wait but never the absolute
  =FLOCAL_MAX_SESSION_SECONDS= deadline or the existing transfer, metadata,
  record, authorization, object-hash, no-follow, capacity, source-snapshot,
  install-intent, or final-transaction limits.  Separately, every nonempty
  outbound connector batch has its fixed 30-second send-and-receipt deadline,
  clamped to that same absolute deadline.  It covers every object and batch-end
  write plus its receipt, and is never renewed by a chunk, partial write, or
  trickle read.  A silent receiver or applier, malformed frame, wrong count,
  early/late batch marker, duplicate request, out-of-order commit progress, or
  oversized control frame fails rather than retaining a live session.
- The responder's existing generic post-snapshot output writer is not
  redesigned here.  New receipts are written only at an accepted bounded
  connector batch boundary, while the connector is already awaiting and
  draining them; apply reports use the absolute-deadline writer described
  above.  They add no unsolicited output stream or output-window flood.
  Making every unrelated legacy one-shot response write deadline-aware remains
  a separate transport change.
- A single blocked object read, record installation, SQLite operation, or final
  install transaction can still produce no frame for 30 seconds.  That is
  intentionally a timeout, not a fictitious progress message.  In particular,
  one =apply_record= may include an indivisible copy, sync, exchange, or
  deletion and legitimately times out if it blocks beyond the idle boundary.
  No frame is emitted before that record is durable or after the loop merely
  waits on the final transaction.

Linux and macOS use the same Rust V1 framing, Unix SSH child, timed reader,
and capability-based object storage code.  Docker is Linux-only test
infrastructure; the protocol grammar, receipt cap, batching, timeout cleanup,
and object-state tests run on both supported platforms.

* 5. Acceptance and fail-to-pass validation

1. The committed known failure and its baseline run establish the exact public
   symptom: the 5,000-file scenario crosses 30 seconds and fails with =peer
   protocol read timed out= plus the connector-caused cleanup suffix.  The
   promoted test retains exit status, stdout, and stderr and treats any
   nonzero result or outer ten-minute target timeout as a failure.
2. Implement version 8, promote that identical Docker scenario by removing
   =known_failure=, raise its external safety deadline to ten minutes for the
   measured two-sided apply, and assert
   successful =sync add=, elapsed time above 120 seconds while the natural
   timing holds, at least three =remote file transfer in progress= lines, at
   least three =remote apply in progress= lines, at least three =local apply in
   progress= lines, responder and connector =pending_install: false= completion,
   and equal trees.
   Captured
   stdout must contain exactly the normal final =Connected ...= line; stderr
   must contain no =Connected= line (it normally contains the expected progress
   lines).  Make =connected_line= lock stdout, write the final line through
   that lock,
   and explicitly flush it, propagating both write and flush failures.  This
   gives an interactive user immediate completion visibility and avoids relying
   on non-TTY stdout buffering.  Add a controlled process-boundary
   delayed-=Connected= test, reusing the current harness where possible: run
   the command in the background with stdout redirected to a harness file,
   hold final installation/apply, poll that file and prove it has no
   =Connected=, then release completion and poll for exactly one normal final
   line.  Add a focused injected-writer test that a flush error from this
   private output path reaches the command result.  Focused apply tests prove a
   failed progress write retains a recoverable durable install intent, and the
   existing interruption-recovery coverage continues to prove that the next
   ordinary sync/watch settles that state.  The README acceptance update tells users that a truthful
   timeout prints no =Connected= and to rerun that ordinary foreground sync
   after connectivity is restored.  It must not use an artificial delay, a
   test-only wire frame, a raised product timeout, or a background-daemon
   shortcut.
3. Add fast V1 unit tests for protocol-version advancement and new-message
   round trips; count, byte, oversized-single-object, short-final, empty, and
   receipt-cap batch boundaries; exact receipt counters and raw-size bounds;
   zero, repeated, regressing, out-of-range, padded, and over-cap apply
   progress; out-of-phase new messages; bounded one-shot errors; callback
   ordering after durability; recoverable callback failure; ordinary and
   managed no-progress wrappers; and responder propagation of the typed
   callback failure.
4. Add real Unix-stream tests showing successful length-aware receipt and
   object framing and a non-reading peer expiring a large
   =send_object_until= operation at its fixed deadline.  Retain the existing
   slow-drip absolute read/write deadline coverage.  Add focused cleanup tests
   proving only typed deadline expiry selects each new phase diagnostic, that
   those diagnostics omit the connector-caused exit-status suffix, and that
   unrelated transfer, apply, and local errors retain their ordinary cause.
5. Run the focused promoted Docker scenario, normal =make e2e= selection,
   =make check= (including whole-project and changed-line coverage), formatting
   and Clippy, Linux CI Docker coverage, and macOS native tests.  Update
   =README.org= in the implementation change to name explicit protocol 8,
   upgrade-both-peers behavior, transfer/apply-progress lines, the truthful
   local timeout with no premature =Connected=, and the ordinary =flocal sync
   PATH --yes= recovery guidance.  Do not change dated historical documents.

* 6. Alternatives rejected

- Raising or removing the 30-second idle limit would hide a stalled receiver
  and leave a hung initial sync without a truthful boundary.
- A responder timer heartbeat or unbounded receiver progress stream would let
  a hostile peer refresh the read timeout without completing an object.  It
  also fails to solve the connector's current write-all-then-read ordering.
- A reader thread while the connector writes would add child ownership,
  channel, cancellation, and error-race machinery.  The existing one-shot
  protocol is naturally turn-based; bounded batch receipts establish the
  needed read boundary with no concurrent SSH access.
- A larger fixture, artificial sleep, or a test-only protocol frame would not
  prove the observed receiver backpressure and would add avoidable CI time or
  production surface.
