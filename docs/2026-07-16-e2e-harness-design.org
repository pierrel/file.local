#+title: End-to-end two-container test harness
#+date: 2026-07-16
#+status: accepted; first slice implemented

* 1. Summary, goals, and non-goals

The alpha implementation state records one standing validation gap: "Real
cross-machine SSH and macOS filesystem acceptance still need to be run"
([[file:2026-07-14-alpha-implementation.org][alpha implementation state]]). Today's closest test, =tests/ssh_sync.rs=,
substitutes a shell script for =ssh= and runs both peers as processes of one
user on one filesystem. That proves the protocol across a process boundary; it
does not prove the product: real binaries, real =sshd=, real key
authentication, two isolated filesystems, and a network that can actually go
away.

This design adds a true end-to-end harness: two Docker containers acting as
real =flocal= peers over real SSH, driven from ordinary Rust tests. The
headline requirement, stated by the user verbatim, is that "the interface for
making changes to files, bringing the containers on and offline, and the like
(the primitives of our use-cases) should be very easy to read and modify
(almost like a very simple dsl)". The scenario-authoring interface is the
product of this feature; the container plumbing exists to serve it.

** Goals

- True end-to-end coverage: released-profile =flocal= binaries, launched
  through a real OpenSSH client and server, between two hosts with independent
  filesystems, state directories, and network presence.
- A scenario vocabulary so small and literal that a new scenario reads as the
  user story it encodes, and a reviewer can verify it against the story
  without reading harness internals.
- First-class coverage of the offline-deletion tombstone-retention story:
  the harness lands first and /pins the bug on =main=/ as a strict expected
  failure (section 2.4), then proves the fix on =agent/tombstone-retention=
  by promoting the scenario from expected-fail to passing — a machine-checked
  fail-to-pass validation, not an assumption that the fixed branch is
  already present.
- Deterministic, condition-based waiting. No fixed sleep is ever load-bearing
  for correctness.
- Debuggability on failure: a failing scenario dumps both trees, both
  statuses, and both container logs without being asked.

** Non-goals

- Replacing unit or existing integration tests. =tests/core.rs=,
  =tests/protocol.rs=, =tests/state_api.rs=, and =tests/ssh_sync.rs= remain
  the fast, always-on gate; the harness is a slower acceptance layer.
- Performance or load testing. Scenarios assert behavior, not throughput.
- macOS containers. Docker cannot run macOS; the macOS half of the acceptance
  gap remains explicitly open (section 11).
- Clock-skew fault injection. Containers share the host kernel clock, so LWW
  skew scenarios are out of scope here (section 10).
- More than two peers /in scenarios/, matching the v0.0.1 share model. It is
  an expected future requirement, so the harness must not box it out
  (section 3.1) — it is simply out of scope to exercise now.

* 2. The scenario DSL

** 2.1 Decision: a small Rust fluent API inside ordinary integration tests

Three alternatives were evaluated:

1. *A Rust fluent API* — scenarios are =#[test]= functions in
   =tests/e2e/=, written against a =Peer= handle with verbs like =write=,
   =offline=, =sync=, =assert_absent=.
2. *An external plain-text scenario format* — a =.scenario= file per story
   plus an interpreter that parses and executes it.
3. *Shell-script helpers* — a =tests/e2e.sh= library of functions sourced by
   per-scenario scripts.

Option 1 is selected. Measured against the engineering principles in
[[file:../AGENTS.md][AGENTS.md]]:

- /Simplicity, no invented abstractions./ Option 2 invents a language: a
  grammar, a parser, an interpreter, error reporting for malformed scenarios —
  a permanent maintenance surface that exists only to avoid writing Rust in a
  Rust repository. Option 1's "DSL" is nothing but well-named methods; there
  is no syntax to maintain.
- /Typo and type safety./ In option 1 a misspelled primitive, a missing
  argument, or a =sync()= call on the wrong peer fails at compile time —
  =cargo test --all-targets= (already in =make test= and CI) type-checks every
  scenario on every run even when Docker is absent. Options 2 and 3 fail at
  runtime, minutes into a container run, or silently (an unset shell variable
  expands to nothing).
- /IDE support./ Scenario authors get completion, jump-to-definition into the
  harness, and rename refactoring for free. Neither alternative offers any.
- /Rust-native tooling./ Scenarios run under =cargo test=, report through the
  standard test harness, and reuse =anyhow= error context. Option 3 would be
  the repository's only shell codebase and reintroduces the quoting and
  word-splitting hazards this project deliberately engineers away at the SSH
  boundary.
- /Readability, the headline requirement./ The examples below are the
  evidence: an option-1 scenario is a straight-line sequence of
  subject-verb-object calls with no ceremony beyond =?=. Option 2 would read
  marginally more "plain" at the cost of everything above; the gap is not
  worth a parser.

One deliberate type-level guardrail: pairing returns distinct types for the
two roles. In v0.0.1-alpha only the connector may initiate =sync= and =watch=
(the responder is launched over SSH on demand), so pairing yields
=(Connector, Peer)= where =Connector= dereferences to =Peer= for the shared
file, connectivity, and assertion vocabulary, and only =Connector= has
=sync()= / =watch_start()=. Calling =sync= on the responder is a scenario
bug the compiler rejects instead of a runtime surprise. This mirrors the
product's real asymmetry rather than inventing one.

Two mechanical rules keep that shape safe. First, every primitive takes
=&self= — the transcript and other bookkeeping live in the shared run context
(section 3.4) behind interior mutability — and no type in the harness
implements =DerefMut=, which is precisely what makes
=Connector: Deref<Target = Peer>= sound; the non-=mut= bindings in the
committed examples are the intended style. Second, =peer_add= /consumes/ the
two raw container handles and returns =(Connector, Peer)=, so a half-paired
topology cannot linger in scope. =pair()= is implemented by calling the same
public primitives — =containers()=, =init()=, =peer_add()=, one confirmed
sync — so the opening logic exists exactly once.

** 2.2 Example scenarios

The first three are the committed scenario bodies (=tests/e2e/scenarios/=);
the watch example (2.2.4) belongs to the unimplemented watch slice and
remains illustrative. =e2e::pair()= performs the standard opening — build
image, start both containers, =init= on peer A, =peer add= toward peer B,

*** Offline deletion is retained and never resurrects

The end-to-end form of the =agent/tombstone-retention= fix
(=offline_deletion_survives_scan_cycles_until_peer_returns= in
=tests/core.rs=), now over real SSH and a real disconnected network. The
body below is its final form; it lands wrapped in =e2e::known_failure=
(section 2.4) until PR #2 merges, and promotion deletes only the wrapper —
a line plus its closing brace:

#+begin_src rust
#[test]
#[ignore = "requires docker; run via `make e2e`"]
fn offline_deletion_propagates_and_nothing_resurrects() -> Result<()> {
    let (a, b) = e2e::pair()?;
    a.write("dir/child", "v1")?;
    a.sync()?;
    b.assert_file("dir/child", "v1")?;

    b.offline()?;
    a.remove_dir_all("dir")?;
    for _ in 0..3 {
        a.sync_expect_offline()?;
    }
    // No paired reservation completed, so status remains the last completed scan.
    a.assert_status(|s| s.entries == 2 && s.tombstones == Some(0))?;
    a.assert_absent("dir")?;

    b.online()?;
    a.sync()?;
    a.assert_absent("dir")?;
    b.assert_absent("dir")?;

    a.sync()?; // steady-state round: retained tombstones must not reapply
    a.assert_absent("dir")?;
    b.assert_absent("dir")?;
    e2e::assert_trees_equal(&a, &b)
}
#+end_src

*** Concurrent offline edits: one winner, loser recoverable

#+begin_src rust
#[test]
#[ignore = "requires docker; run via `make e2e`"]
fn concurrent_edit_keeps_one_winner_and_a_recoverable_loser() -> Result<()> {
    let (a, b) = e2e::pair()?;
    a.write("notes.txt", "base")?;
    a.sync()?;

    b.offline()?;
    a.write("notes.txt", "edit from a")?;
    b.write("notes.txt", "edit from b")?;
    b.online()?;
    a.sync()?;

    // Both peers show the same deterministic winner; which side wins depends
    // on discovery-scan ordering, so only recoverability is asserted.
    e2e::assert_trees_equal(&a, &b)?;
    let conflicts = a.conflicts()?;
    let conflict = conflicts.expect_one("notes.txt")?;
    let winner = a.read("notes.txt")?;
    let loser = a.restore_loser(&conflict.id)?;
    let mut both = [winner, loser];
    both.sort();
    anyhow::ensure!(
        both == ["edit from a", "edit from b"],
        "winner and loser must preserve both inputs, got {both:?}"
    );
    Ok(())
}
#+end_src

The scenario asserts that a deterministic winner exists on both peers and
that the losing input is fully recoverable; it does not assert /which/ side
wins, because the alpha stamps an offline edit at discovery-scan time
(documented in the alpha implementation state), so the winner depends on
scan ordering, not on which =write= line appears first.

*** Basic bidirectional sync of every supported entry kind

#+begin_src rust
#[test]
#[ignore = "requires docker; run via `make e2e`"]
fn files_directories_symlinks_and_exec_bits_sync_both_ways() -> Result<()> {
    let (a, b) = e2e::pair()?;
    a.write("src/lib.txt", "from a")?;

    b.assert_exec("run.sh")?;
    b.assert_symlink("current", "src/lib.txt")?;

*** Watch notices an editor-style atomic-rename save

A later-slice scenario (catalog #13); it requires the
=FLOCAL_WATCH_RESCAN_SECONDS= hook of section 14.1, which is not needed for
S1:

#+begin_src rust
#[test]
#[ignore = "requires docker; run via `make e2e`"]
fn watch_notices_an_atomic_rename_save() -> Result<()> {
    let (a, b) = e2e::pair_with(e2e::Config { watch_rescan_seconds: 1 })?;
    a.write("notes.txt", "v1")?;
    a.sync()?;

    let watch = a.watch_start()?;
    a.write(".notes.txt.tmp", "v2")?; // editor safe-save: temp file...
    a.rename(".notes.txt.tmp", "notes.txt")?; // ...renamed over the original
    b.wait_for_file("notes.txt", "v2")?; // the assertion: fails (with the dump)
    watch.stop()                         // if v2 never arrives by the deadline
}
#+end_src

The =wait_for_file= call /is/ this scenario's assertion — a =wait_*=
primitive is an assertion with a deadline (section 2.3), so a scenario whose
only checks are =wait_*= calls asserts plenty.

** 2.3 The primitive vocabulary

Everything a scenario may say. Receiver prefixes are the convention
throughout: =a.= marks connector-only verbs, =p.= verbs available on either
peer. Each primitive is one short method; the full set is deliberately
enumerable on one page.

*Peer file operations* (executed inside the container as the unprivileged
user; paths are share-relative and validated by the harness — section 9):

| =p.write(path, content)=    | create or replace a file, creating parents    |
| =p.read(path) -> String=    | read a file                                    |
| =p.mkdir(path)=             | create a directory (and parents)               |
| =p.rename(from, to)=        | rename within the share (atomic-save pattern)  |
| =p.remove(path)=            | delete a file or symlink                       |
| =p.remove_dir_all(path)=    | delete a directory tree                        |
| =p.symlink(path, target)=   | create a symlink with the given target text    |
| =p.set_exec(path)= / =p.unset_exec(path)= | set or clear the executable bit  |
| =p.write_bytes(path, bytes)= | create or replace a file with arbitrary, possibly non-UTF-8 bytes |

=write()= (and =write_bytes()=, the same mechanism) streams content over
stdin to =tee= and is deliberately /not/
atomic: a running =watch= may observe a partially written file, exactly as
it may with a real editor — a representative interleaving, not a harness
defect. Watch-mode scenarios therefore assert only eventual states through
the =wait_*= primitives, never intermediates. When a scenario needs an
atomic mutation it composes it the way editors do — =write= to a temporary
name, then =rename= — which stays within the same directory and mount.

*Lifecycle* (each maps to exactly one =flocal= invocation or Docker action):

| =e2e::containers() -> (PeerBox, PeerBox)= | started, unpaired containers — for pairing/rejection scenarios |
| =e2e::pair() -> (Connector, Peer)=        | the standard opening: init, peer add, confirmed initial sync |
| =e2e::pair_with(Config)=                  | same, with knobs (currently: watch session byte limit) |
| =a.init()= / =a.peer_add(b) -> (Connector, Peer)= | explicit pairing steps; =peer_add= is a =PeerBox= method consuming both boxes |
| =a.sync()=                                | =flocal sync --yes=; fails the scenario on nonzero exit |
| =a.sync_dry_run()=                        | =flocal sync --dry-run=; asserts the connector's tree is unchanged by the preview |
| =a.sync_decline()=                        | =flocal sync= without =--yes=, declining the initial confirmation |
| =a.sync_expect_offline()=                 | asserts nonzero exit and that the connector's tree is unchanged |
| =a.sync_expect_err(needle)=               | asserts nonzero exit and a substring of stderr |
| =a.watch_start() -> Watch= / =watch.stop()= | foreground =flocal watch= held by a guard |
| =a.watch_start_with_apply_stop() -> Watch= / =watch.wait_stopped()= | E2E-feature watch with a one-shot deterministic pre-apply stop |
| =p.status() -> Status=                    | parsed =status --json= (=schema=, =entries=, =pending_install=, =tombstones=, and =unsettled=; fields grow with the scenarios that read them) |
| =p.conflicts() -> Conflicts=              | either peer's parsed =conflicts list --json=, with =expect_one(path)= |
| =p.restore_loser(id) -> String=           | either peer's =restore --version loser= to a scratch path outside the share; returns the content |
| =p.reset_state()=                         | delete the peer's flocal state directory (=~/.local/state/file.local=) inside its container, so it no longer holds the share registration or peer binding, while its share files and the other peer's registration of it survive |
| =e2e::known_failure(body)=                | strict expected-failure wrapper for scenarios pinning known-broken behavior on =main= (section 2.4) |

=sync()= returns =Result<()>= — no report type is introduced until a
scenario consumes one. A sync that records a conflict exits 0 and is a
successful =sync()=; "fails on nonzero exit" refers to transport and apply
errors.

Three lifecycle contracts deserve spelling out:

- =sync_decline()= is meaningful only /before/ the initial confirmed sync:
  the confirmation prompt is gated on incomplete initial reconciliation in
  =src/main.rs=. The primitive feeds "n" up-front over the exec's stdin,
  then asserts after exit that the =[y/N]= prompt actually appeared on
  stdout, that the exit was clean, and that the connector's tree is
  unchanged — the same fail-loudly guarantee as observing the prompt live,
  with a simpler mechanism. Because the prompt must have appeared, misuse
  after =pair()= fails loudly instead of passing vacuously.
- =sync_expect_offline()= asserts /no/ error text — only the nonzero exit
  and the connector's unchanged tree. On an unreachable peer the product
  surfaces only a generic connection/EOF failure (the SSH session's stderr
  is surfaced by the product only on the clean-exit path), and the design
  does not promise more than the product prints. It and =sync_expect_err()=
  are separate functions layered over the same raw-invocation helper.

Both =sync_decline()= and =sync_expect_offline()= — and =sync_dry_run()= —
check the /connector's/ tree only, because their signatures cannot reach
the other peer; scenarios assert the responder side explicitly (as
catalog #2 does with =b.assert_absent=).
- =watch.stop()= terminates the watcher /inside/ the container: a second
  =docker exec= signals the recorded PID and waits for it to exit, because
  killing the =docker exec= client does not kill the exec'd process, and a
  surviving watcher would keep holding its share-session lock and any active
  round permit. Even
  SIGKILL is lock-safe by the product's own construction: =flock= releases
  on process exit, SQLite WAL recovers, and =recover_installs= attempts to
  repair an interrupted install on the next command.  The stale-intent bug
  originally pinned by =watch_does_not_remain_stuck_on_a_stale_install_intent=
  is now repaired and that scenario passes; see the 2026-08-12 update below.
  =stop(self)= consumes the guard,
  so double-stop is unrepresentable; the guard's =Drop= is the
  never-panicking best-effort backstop.

=Status= and =Conflicts= deserialize the product's own JSON and
assert that the embedded =schema= field equals a constant pinned in the
harness, failing with the actual version on mismatch, so a schema bump
breaks scenarios mechanically and visibly rather than silently misparsing.
The conflicts listing has its own pinned constant (=CONFLICTS_SCHEMA=,
currently 1), independent of the status pin, so the status bump to 3 does
not disturb conflicts parsing.
The pinned constant tracks /=main= at harness landing/: status schema 1,
which has no =tombstones= field. So that one =Status= struct is final form
across the bump, =tombstones= is declared =Option<u64>= — =None= under
schema 1, populated from schema 2 — and scenarios assert against
=Some(count)= (example 2.2.1). On =main=, #6's tombstone assertion finds
=None=, fails, and satisfies its =known_failure= wrapper (section 2.4); the
tombstone pull request bumps the pinned constant to 2 in the same change
that promotes its six scenarios (section 14.4). An implementer must /not/ "helpfully" pin
schema 2 at harness landing — that would break the nine scenarios that
pass on =main=. Diagnostics never depend on any of this: the section 8
failure dump prints the /raw/ =status --json= output without parsing it, so
a schema mismatch — or a status that fails to parse at all — is itself
visible in the dump rather than able to break it.

*Connectivity:*

| =p.offline()= | detach the container from the shared network (section 4) |
| =p.online()=  | reattach it, restoring its DNS alias                      |

*Time — always a condition plus a bounded timeout, never a bare sleep:*

| =p.wait_for_file(path, content)=  | poll until present with content, or dump and fail at the deadline |
| =p.wait_absent(path)=             | poll until absent |
| =p.wait_status(predicate)=        | poll =status --json= until the predicate holds |

Default deadline 30 seconds, poll interval 250 ms, both overridable per call.
The =wait_*= primitives /are/ assertions — each fails the scenario, with the
section 8 dump, when its deadline expires — so a watch scenario whose only
checks are =wait_*= calls is fully asserted. Because =flocal sync= is
synchronous, most scenarios need no waiting at all; the wait primitives
exist for =watch=-mode scenarios and reconnection races.

*Assertions* (each failure names the peer and, where the primitive knows
them, the path plus expected and actual values — =assert_status= shows the
peer and the full parsed status, since a closure predicate cannot print its
own expectation — and triggers the failure dump of section 8):

| =p.assert_file(path, content)= | exists, is a regular file, content matches |
| =p.assert_absent(path)=        | no entry of any kind at the path |
| =p.assert_dir(path)= / =p.assert_exec(path)= / =p.assert_not_exec(path)= / =p.assert_symlink(path, target)= | kind- and metadata-specific |
| =e2e::assert_trees_equal(&a, &b)= | full-tree comparison of kind, content hash, exec bit, link target |
| =p.assert_status(predicate)=   | one assertion over the parsed status |

Drift between an assertion and its wait form is prevented structurally, not
by convention: each check exists exactly once, as a named =Condition= — a
probe closure plus a describe string — and the public =assert_x(...)= and
=wait_x(...)= are two thin entry points over the /same/ =Condition=
constructor, with =assert_x= literally calling the wait implementation with
a zero deadline. One comparator per check, so the immediate and eventual
forms cannot diverge by construction.

=assert_trees_equal= and every failure dump are fed by a harness-internal
tree walk that is deliberately /not/ scenario-facing vocabulary. Its
comparison mirrors what the product actually synchronizes: it excludes
=.git= and any =.flocal-tmp-*= component exactly as the scanner does;
records the executable bit as the boolean the product syncs
(=mode & 0o111 != 0= — full permission modes legitimately differ across
peers); hashes regular-file content only; records symlink target text from
an =lstat=-based walk that never follows links, so a dangling link is
representable; and treats empty directories as first-class entries. The
harness never names its own staging files with the product-owned
=.flocal-tmp-= prefix.

Exit codes and errors are asserted through the =sync_expect_*= lifecycle
verbs rather than a general shell primitive, keeping scenarios declarative.
A scenario that needs a new primitive adds one method to the harness; it
never shells into a container directly.

** 2.4 Strict expected failure: =known_failure=

The accepted delivery order is harness first, off =main=, with zero
product-code prerequisites — which means some scenarios encode behavior
that is /known broken/ on =main= today. Those scenarios land wrapped:

#+begin_src rust
#[test]
#[ignore = "requires docker; run via `make e2e`"]
fn offline_deletion_propagates_and_nothing_resurrects() -> Result<()> {
    e2e::known_failure(|| {
        // the pristine scenario body of example 2.2.1, unchanged
    })
}
#+end_src

=known_failure(body)= runs the scenario closure and inverts the verdict,
strictly — the analog of pytest's =xfail(strict=True)=:

- If the closure returns =Err= (any primitive or assertion fails), the test
  /passes/: the known bug is still pinned. The section 8 failure dump is
  suppressed, because the failure is the expected outcome.
- If the closure succeeds, the test /fails/, with the message "scenario now
  passes — promote it to a plain test in this PR".

One carve-out keeps the pin honest: a failure of the harness /itself/ — the
daemon check, stale-run sweep, image build, or any container, network, or
key setup before the first scenario primitive — is typed (=InfraError=) and
re-raised out of =known_failure= instead of satisfying it, so an
infrastructure flake cannot turn a pinned scenario vacuously green.

This is what keeps =main='s e2e run green while continuously pinning each
known bug, and what forces the fixing pull request to flip the scenario in
the same change — a machine-checked fail-to-pass validation. The fix cannot
merge without deleting the wrapper, and the wrapper cannot outlive the fix.
Promotion is exactly one edit — delete the wrapper, a line plus its closing
brace — because every wrapped scenario body is already written in its
final, post-fix form.

* 3. Container topology and lifecycle

** 3.1 Topology

One user-defined Docker bridge network and two containers per scenario, with
synthetic in-network aliases =peer-a= and =peer-b=. Real container and network
names carry a per-run unique token (=flocal-e2e-<run>-peer-a=,
=flocal-e2e-<run>-net=) plus a
=flocal-e2e=1= label so cleanup can never touch unrelated containers.
User-defined networks provide embedded DNS, so container A reaches B as
=peer-b= — no IP addresses appear anywhere, satisfying the no-real-hosts rule
by construction.

Each container is started with =--rm= and runs
=timeout <lifetime> /usr/sbin/sshd -D -e= as PID 1 — root, as sshd requires
for privilege separation; sessions log in as the unprivileged =peer= user
created at image build (the root/non-root split section 9 describes). The
lifetime is env-tunable — =docker run= forwards a host-set
=FLOCAL_E2E_CONTAINER_LIFETIME_SECONDS= into the container, defaulting to
3600: when it expires, PID 1 exits and =--rm= removes the container, so
every container self-terminates and self-removes within the bound with no
external actor — even if the harness process is SIGKILL'd or hangs.
The share root is
=/home/peer/share=; =flocal= state lands in the real default
=~/.local/state/file.local= — no =FLOCAL_STATE_DIR= override, because the
point is exercising defaults.

Each container mounts its own named Docker volume — two per run, one per
peer, so the peers' filesystems stay fully independent (labeled
=flocal-e2e=1= and removed with the run) — at =/home/peer=, so the share
root /and/ the state directory live on a real host filesystem rather than
the container's overlay2 layer. This is a correctness decision, not a convenience: =flocal=
depends on =RENAME_EXCHANGE= / =RENAME_NOREPLACE= semantics and on inotify
delivery, and overlayfs — especially fuse-overlayfs under rootless Docker —
is an environment hazard for exactly those, which would masquerade as
product bugs. A tmpfs mount was rejected because =fsync= there is a no-op,
quietly weakening the durability behavior the product exercises. Named
volumes behave identically under rootful and rootless Docker.

Containers are started with modest =--memory= and =--pids-limit= caps, so a
regressed binary that leaks memory or forks unboundedly dies inside its own
container — producing a scenario failure with the section 8 dump — instead
of wedging the developer machine or CI runner.

Nothing in this topology hardwires "two". More than two peers is an
expected future requirement, and the harness keeps that door open
structurally: each peer is an independent handle over its own container and
volume; the network holds N containers as readily as two; the
=peer-a=/=peer-b= naming generalizes to =peer-N=; and =pair()= is a
convenience over =containers()=, which can grow an N-ary form when a story
needs one. The one deliberately v0.0.1-shaped piece is the
=Connector=/=Peer= type split, which encodes the alpha's initiator
asymmetry — revisited, not entrenched, when topologies change.

** 3.2 Image

There is deliberately no product image for this to share: =flocal= ships as
a single binary installed on ordinary hosts and reached over SSH
(=make install=), so no deployment image exists for the harness to consume.
The test image is therefore test infrastructure — =sshd=, an unprivileged
user, and the binary built from the same source tree — not a parallel
product definition. If the product ever gains a shipped image, the harness
should consume it and layer only the test-specific pieces on top.

One image serves both peers, built by a multi-stage Dockerfile at
=tests/e2e/Dockerfile=:

- *Builder stage:* =rust:1-bookworm= (the tag names the base here for
  readability; the Dockerfile itself references it by manifest-list digest,
  as below), =cargo build --release --locked= of the repository source.
  Dependencies build first against a dummy source tree in their own layer,
  so a source-only change rebuilds only the crate itself; this ordinary
  layer caching replaced the originally proposed BuildKit cache mounts
  because it works identically on the legacy builder and BuildKit, dropping
  BuildKit as a host prerequisite.
- *Runtime stage:* =debian:bookworm-slim= (likewise digest-pinned in the
  Dockerfile) plus =openssh-server=, =openssh-client=, and =bash=; copies
  the binary in, creates the =peer= user, generates host keys, and installs
  the =flocal= entry point as the thin stderr-teeing wrapper described in
  section 8, with the lifetime-bounded =entrypoint.sh= as PID 1.

The build context is minimal and explicit: the Dockerfile =COPY=s
=Cargo.toml=, =Cargo.lock=, =src/=, and the two runtime scripts
=tests/e2e/entrypoint.sh= and =tests/e2e/flocal-wrapper.sh= — nothing else
is needed — with a =.dockerignore= (=.git=, =target=, =docs=,
=references=, =tests=, plus negations re-admitting exactly those two
scripts) enforcing it. The repository previously had no =.dockerignore=,
so a naive =COPY . .= would ship =.git=, a multi-gigabyte =target/=,
and any stray developer-local file into cached builder layers; the explicit
COPY list makes that impossible rather than merely unlikely, and section 12
makes it an acceptance criterion.

Building on the host and copying the binary in was rejected: the developer
host and CI runner link against a newer glibc than a stable slim base, so a
host-built binary can fail to load in the container — an environment bug
masquerading as a product bug. A musl static build would avoid that but adds
a host cross-toolchain requirement (=rusqlite= bundles C). Building inside
the image is hermetic and needs nothing but Docker.

The base images are pinned by digest, matching this repository's convention
of pinning CI actions by hash — specifically by /manifest-list/ digest, not
a single-architecture image digest, so Docker Desktop on an Apple-silicon
macOS development host resolves them and =make e2e= works there too (Linux
containers on a macOS host; distinct from the macOS /CI/ limitation in
section 11). Pinned bases are the smaller half of the supply-chain story:
the real build-time fetch surface is crates.io — pinned by =Cargo.lock= and
enforced by =--locked= — and Debian's signed apt repositories.

One honesty note on caching: the dependency layer delivers seconds-warm
rebuilds on local machines and persistent runners (the Forgejo target
environment). GitHub-hosted CI runners are fresh VMs — no image layer cache
survives between runs — so CI runs build cold and are budgeted for it
explicitly (section 12).

** 3.3 Keys and SSH configuration

Per run, the harness generates a throwaway ed25519 client keypair with
=ssh-keygen= into the run's temporary directory — never written into the
repository, never reused across runs. Provisioning is /symmetric/: the
public key goes into =peer='s =authorized_keys=, and the private key plus a
=~/.ssh/config= stanza are installed into /both/ containers, because either
raw container may become the connector — =a.peer_add(b)= or
=b.peer_add(a)=:

#+begin_example
Host peer-a peer-b
    User peer
    IdentityFile ~/.ssh/id_ed25519
    StrictHostKeyChecking accept-new
#+end_example

so =flocal peer add /home/peer/share --host peer-b --remote-path
/home/peer/share= exercises the documented alias flow exactly. The security
rationale is unchanged by the symmetry: the key is throwaway and per-run,
the bridge network is isolated, and the containers self-terminate — the
extra responder-to-connector trust direction is test-only surface the
product never exercises.
=accept-new= is safe here because the network is isolated and the host key
is fixed at image build; it also keeps the first connection non-interactive.
Pairing's =command -v flocal= discovery probe runs for real against the
container's =sshd=.

** 3.4 Lifecycle, ownership, and cleanup

Fresh containers per scenario (creation is 1–2 seconds against a built
image); no state leaks between scenarios by construction.

Ownership is explicit. A single run context, shared by =Arc=, owns the
network, the two per-peer volumes, the temporary directory and keys, the
transcript, and a dumped-once flag. Each peer handle's =Drop= force-removes
only its own container; the context's =Drop= — the last =Arc= clone —
removes the network and both volumes. Every =Drop= — containers and
context alike — logs its failures and never panics: a panicking =Drop=
during unwind would abort the process and lose the failure dump. On
unwind, the /first/ container dropped triggers the dump while both
containers are still alive — that is how "dump before cleanup" is
delivered — and an ordinary panic (every failed assertion) then cleans up
in order.

Two backstops cover what =Drop= cannot. =make e2e= begins by removing
anything labeled =flocal-e2e=1= left behind by an aborted earlier run; the
sweep is =rm=-only as an invariant — it never runs =exec= or =logs= against
swept objects. And =FLOCAL_E2E_KEEP=1= disables cleanup deliberately for
post-mortem inspection (the failure dump prints the container names when
set; the preserved containers are still bounded by the section 3.1
lifetime). The sweep implies a stated assumption: one =make e2e= run per
host at a time — two simultaneous runs would sweep each other's live
containers.

The bounded container lifetime of section 3.1 is the deepest backstop, and
the answer to "is cleanup resilient even when normal teardown never runs":
a SIGKILL'd or wedged harness process still leaves no long-lived container,
because PID 1's =timeout= plus =--rm= self-terminate and self-remove each
container within the bound, with no external actor. Networks and volumes
cannot self-remove, but they are inert — no process, no CPU, no memory —
and the next run's label sweep removes them.

* 4. Connectivity control

=offline()= is =docker network disconnect <net> <container>=; =online()= is
=docker network connect --alias <that peer's alias> <net> <container>= —
the primitive is peer-generic, so reattaching peer A restores =peer-a= and
peer B restores =peer-b=. The failure-mode comparison:

- *=docker network disconnect= (chosen):* removes the container's interface
  and its embedded-DNS entry. The next SSH attempt fails immediately with
  name-resolution or no-route errors; =flocal sync= exits nonzero within a
  second with a generic connection/EOF failure — which is why
  =sync_expect_offline()= asserts only the nonzero exit and the connector's
  unchanged tree (section 2.3). Deterministic, fast, needs no privileges beyond the Docker
  access the harness already has, and works identically under rootful and
  rootless Docker.
- *iptables/nftables rules:* requires =NET_ADMIN= in the containers or root
  on the host, and can emit either RST (refused) or silent drops (hangs)
  depending on rule shape — more fidelity knobs than any current scenario
  needs, at real privilege cost.
- *=docker pause=:* freezes processes but the kernel still completes TCP
  handshakes, so the SSH client connects and then stalls in the protocol
  until =ServerAliveInterval= expires (~30–45 s with the options in
  =src/main.rs=). Slow, and it models a hung peer rather than an absent one.

All current stories need exactly one semantic — "peer unreachable" — and
disconnect produces it in its cleanest, fastest form. If a future story needs
hang-versus-refused distinctions, a second primitive can be added without
disturbing =offline()='s meaning. One subtlety is handled inside =online()=:
reconnection may assign a different IP, which is invisible to scenarios
because peers address each other only by their configured DNS aliases, and
the harness re-supplies the reattaching peer's own alias on reconnect.

* 5. Runner integration

** 5.1 Invocation

Scenarios are ordinary integration tests under =tests/e2e/= marked
=#[ignore = "requires docker; run via `make e2e`"]=. New Makefile target:

#+begin_example
e2e:
	cargo test --test e2e -- --ignored --test-threads=1
#+end_example

Host prerequisites, each failing with a one-line diagnosis: a reachable
Docker daemon (legacy builder or BuildKit — the Dockerfile requires
neither specifically), checked once per process before the stale-run sweep
and image build; and the OpenSSH client tools on the host (=ssh-keygen=,
for the throwaway keypair), discovered at the first scenario's setup,
after the sweep and build.

=#[ignore]= was chosen over a Cargo feature flag because it keeps the
harness and every scenario compiling in the ordinary =cargo test
--all-targets= path (=make test= and the CI test job), so type errors surface
on machines without Docker, while never executing there. A feature flag
would exclude the code from compilation exactly where compile checking is
wanted.

=make check= is unchanged and must remain green with no Docker daemon
present. Coverage exclusion is explicit and must land in /both/ places the
coverage command lives — the Makefile =coverage= target and the separate
=cargo llvm-cov= line in the =.github/workflows/ci.yml= coverage job — each
gaining =--ignore-filename-regex 'tests/e2e/'= so the
never-executed-under-coverage harness and scenario lines appear in neither
=coverage.xml= denominator. Otherwise unexecuted e2e lines would
mechanically sink the 90% project-wide and changed-line thresholds.
=tools/check_changed_coverage.py= reads =coverage.xml=, so the exclusion
covers both gates. This design's recommendation: converge the CI job onto
=make coverage= so the flag lives in one place.

** 5.2 Docker access

The harness drives the =docker= CLI via =std::process::Command= with argument
vectors — the same pattern =src/main.rs= uses for =ssh=. Alternatives:

- *testcontainers:* built for the throwaway-container use case, but brings an
  async runtime and a generic container-management model; the harness needs
  roughly eight docker verbs (=build=, =network create/rm=, =run=, =exec=,
  =cp=, =network connect/disconnect=, =rm -f=, =logs=).
- *bollard:* a full async Docker API client; the largest dependency for the
  smallest need.

The dependency-fit principle (maintained, /narrow/ dependencies) points at
the CLI: it is the interface Docker documents for exactly these operations,
errors arrive as readable stderr the failure dump can show verbatim, and
the harness stays compatible with any daemon the CLI supports (a
Docker-CLI-compatible podman likely works, though it is not a supported
claim — section 14). No new crate is added.

** 5.3 Serial execution

First slice runs scenarios serially (=--test-threads=1=). Unique per-run
names mean parallelism would not collide, but serial keeps failure dumps
unentangled, resource usage flat on small CI runners, and the first
implementation simpler. Parallel execution is a later optimization,
unlocked by the naming scheme already in place (section 14).

* 6. Timing and flakiness strategy

Two rules:

1. *Scenarios drive =flocal sync= explicitly.* It is synchronous, so a
   scenario is deterministic end to end: act, sync, assert — no waiting.
   The repeated =sync_expect_offline()= calls prove that failures before the
   paired installation reservation do not mutate the persisted scan.  The
   successful round after reconnection rescans, creates the tombstones, and
   propagates the deletion; this keeps the headline scenario deterministic.
2. *=watch= gets a small testability hook and few scenarios.* The watch loop
   hardcodes its 30-second rescan (=rx.recv_timeout(Duration::from_secs(30))=
   in =src/main.rs=), which would make every watch scenario cost tens of
   seconds. Product-code change, requiring sign-off and needed only for the
   later-slice watch scenarios — not for S1 (section 14.1): read
   =FLOCAL_WATCH_RESCAN_SECONDS= with a default of 30 and a clamped floor of
   one second — zero or an unparseable value falls back to the default. The
   clamp is a deliberate, stated deviation from the unclamped
   =FLOCAL_MAX_SESSION_SECONDS= / =FLOCAL_MAX_STATE_BYTES= /
   =FLOCAL_MAX_SESSION_BYTES= siblings, because a zero interval would
   hot-loop full rescans and connection attempts, and no scenario or story
   needs it. A handful of scenarios then cover the watch-specific behaviors
   (event-driven save pickup, offline/reconnect catch-up); everything else
   uses explicit sync.

Every wait in the harness is a predicate polled at 250 ms under a bounded
deadline (default 30 s); a deadline expiry produces the full failure dump,
not a bare timeout. Fixed sleeps are forbidden as correctness mechanisms —
the only fixed sleep in the harness is the poll interval itself (the
product's own 250 ms watch debounce is its own concern, outside this rule's
scope). This is
the same "no sleep-loop as correctness" discipline the project already
applies elsewhere.

* 8. Interfaces and code layout

The crate remains single-package; no workspace is introduced. A separate
harness crate was considered and rejected: nothing outside the e2e tests
consumes the harness, and Cargo integration-test binaries already provide
the needed isolation. Layout:

#+begin_example
tests/e2e/
  main.rs            declares the scenario and harness modules
  scenarios/
    mod.rs           the scenario catalog: one module per story area
    pairing.rs, syncing.rs, offline.rs, conflicts.rs, ignores.rs, transitions.rs
  harness/
    mod.rs           the public vocabulary re-exports
    docker.rs        docker CLI invocation and the shared RunContext (run-id,
                     network, volumes, keys, transcript, dumped-once flag),
                     InfraError, the stale-run sweep, and the image build
    peer.rs          PeerBox/Connector/Peer: file ops, lifecycle, connectivity,
                     Conditions/assertions, status and conflicts parsing
    dump.rs          failure diagnostics
  Dockerfile
  entrypoint.sh      container PID 1: lifetime-bounded sshd
  flocal-wrapper.sh  tees flocal stderr to the log the dump collects
#+end_example

At this initial dated slice the implemented public surface came out /tighter/
than designed: =mod.rs= re-exported four names: =pair=, =containers=,
=known_failure=, and =assert_trees_equal=. =init= and =peer_add= are methods on the returned
=PeerBox= handles, every other verb is a method on =Connector= or =Peer=,
and the types themselves (=PeerBox=, =Connector=, =Peer=, =Status=,
=Conflicts=) are reachable only by inference from those entry points.
=pair_with=, =Config=, and =Watch= arrive with the watch slice. Everything
in =docker.rs= is private to the harness; a scenario physically cannot
issue a raw docker command through its API. Every primitive takes =&self= —
mutable bookkeeping lives in the run context behind interior mutability —
and no harness type implements =DerefMut= (the rule that keeps
=Connector: Deref<Target = Peer>= sound, section 2.1).

*Failure reporting is a first-class requirement.* Every docker invocation
appends one command/exit-status/duration line to the run transcript. When a
scenario fails — a failing primitive, a failed assertion, or a wait
deadline — the harness prints, while both containers are still alive: the
transcript tail; each container's raw =find= listing of the share
(deliberately unfiltered, unlike the comparison tree walk, so reserved and
ignored names are visible); each container's raw =status --json= output,
printed unparsed so the dump works whatever schema the binary emits; each
container's captured flocal stderr log; and =docker logs= (sshd's stderr).
The stderr log needs one image provision: the =flocal= entry point is a
thin wrapper (=flocal-wrapper.sh=) that execs the real binary with stderr
both forwarded unchanged and appended to an in-container log — on the
responder, whose stderr the connector discards whenever it bails early,
and equally on the connector, so both sides' product diagnostics survive
into the dump.

Dump emission is exactly-once, guarded by the run context's flag: it fires
at the first failing primitive, or at unwind (=std::thread::panicking=,
checked by the first container's =Drop=) for a panic that bypassed the
harness — except inside =known_failure=, where failure is the expected
outcome and the dump is suppressed (section 2.4). One accepted residual: a
scenario-authored plain =Err= (=ensure!=/=bail!= written directly in a
scenario body, as #9 does) reports through the test harness without the
dump, since no failing primitive is involved. With =FLOCAL_E2E_KEEP=1= the
harness additionally preserves the containers and prints their names for
manual =docker exec= inspection. A failing scenario — including a
responder-side failure — must be diagnosable from its CI log alone.

* 9. Security boundaries

- *Throwaway keys only.* The ed25519 keypair is generated per run into the
  run's temporary directory — created mode 0700, with =ssh-keygen= writing
  the private key 0600 — and destroyed with it. No key material, host key,
  or =authorized_keys= content is ever committed; the Dockerfile generates
  host keys at build time inside the image.
- *No host exposure.* Neither container publishes any port (=-p= is never
  used). SSH travels only on the run's internal bridge network. The host's
  own =sshd=, =~/.ssh=, and SSH agent are untouched — the harness never uses
  the developer's SSH identity.
- *Synthetic names only.* =peer-a=, =peer-b=, =/home/peer/share= — no real
  hostnames, addresses, or personal paths in scenarios, harness, or dumps,
  per the AGENTS.md rule.
- *Non-root inside containers.* =flocal= and =sshd= sessions run as the
  unprivileged =peer= user; only PID-1 =sshd= is root, as in a real
  deployment.
- *Input discipline in the harness itself.* Scenario paths are validated
  (relative, no =..=, no leading =-=, no NUL) and passed as distinct argv
  elements — with a =--= separator wherever the tool accepts one; the
  =test= and =readlink= probes pass the already-validated absolute paths
  without it. File content and interactive answers (the "n" that
  =sync_decline()= feeds to the confirmation prompt) travel over the
  =docker exec -i= stdin as data, never through a shell string. The harness
  applies the same no-interpolation rule the product applies at its SSH
  boundary.
- *Docker assumptions.* The harness requires only ordinary access to a
  Docker daemon. Rootful and rootless Docker both support every operation
  used (build, run, exec, volumes, network connect/disconnect). It does not
  require =--privileged=, added capabilities, or host networking. Membership
  in the =docker= group is root-equivalent on the host; the harness does not
  widen that existing exposure — it runs no third-party images beyond the
  digest-pinned bases, and its build-time fetches are pinned or signed
  (section 3.2).

* 10. Failure modes

- *Docker absent or daemon down.* =make check= and =cargo test= are
  unaffected by construction (=#[ignore]=). =make e2e= fails fast: the
  harness's first act checks the daemon (then sweeps and builds, once per
  process — section 5.1), and failure produces a one-line diagnosis
  ("docker daemon unreachable; the e2e suite requires docker") rather than
  a cascade — typed as infrastructure so it can never satisfy a
  =known_failure= pin (section 2.4).
  Failing rather than skipping is deliberate: invoking =make e2e= expresses
  intent, and a silently-skipped suite that reports success is a false
  green.
- *Image pull flakiness.* Both base images are pinned by manifest-list
  digest; a pull failure is a hard, clearly-attributed error. Digest bumps
  are ordinary reviewed commits (cadence: section 14).
- *Container clock skew.* Structurally impossible here: containers share the
  host kernel clock, so LWW timestamps are mutually consistent. This is an
  anti-flake property and a coverage limit — skewed-clock LWW behavior is
  explicitly not tested by this harness (a =libfaketime=-style injection
  could add it later; out of scope).
- *Leftover state.* Per-scenario containers, per-run unique names, ordered
  =Drop= cleanup on panic, and the =rm=-only label sweep at =make e2e= start
  (section 3.4). A hard-killed test process leaves containers that
  self-terminate within the section 3.1 lifetime bound, plus inert networks
  and volumes the next run's sweep removes — under the stated
  one-run-per-host assumption.
- *CI resource limits.* Two slim, resource-capped containers and a serial
  schedule fit the standard runner comfortably. The dominant cost is the
  image build: warm in seconds on local and persistent runners, cold on
  GitHub-hosted runners and budgeted for it in section 12.
- *Slow machines.* All waits are condition-based with generous deadlines, so
  slowness costs seconds, not correctness. A deadline expiry produces the
  full dump, making "slow" and "broken" distinguishable from the log.

* 11. Platform and CI

A new =e2e= job in CI runs =make e2e= on =ubuntu-latest=, where Docker is
preinstalled. The job is Linux-only: GitHub's macOS runners provide no
Docker daemon, and macOS cannot be containerized regardless. (A developer on
a macOS machine with Docker Desktop can still run =make e2e= locally —
Linux containers — per section 3.2.)

Consequence for the acceptance gap, stated plainly: this harness closes the
"real cross-machine SSH" gap for Linux–Linux only. The macOS side of
acceptance criterion 11 — real macOS filesystem semantics (normalization,
case-insensitivity, FSEvents) over SSH — remains open and is *not* covered
or approximated by this feature. The existing macOS CI job continues to
cover unit and non-Docker integration tests; full macOS acceptance remains a
manual (or future dedicated-hardware) task.

Forgejo migration: the job's substance is =make e2e= — plain Docker CLI plus
cargo, no GitHub-specific services, containers, or action semantics. The
only Actions-specific pieces are checkout and toolchain setup, both of which
have direct Forgejo Actions equivalents. One infrastructure prerequisite to
plan for: Forgejo runners need Docker-daemon access configured (a socket
mount, DinD, or a host-labeled runner) — a property of the job's
environment, not of the harness. The upside is that persistent Forgejo
runners are exactly where the cached dependency layer delivers warm builds.

* 12. Acceptance criteria for the first slice

The harness's first implementation is acceptable when:

1. =make e2e= on a Linux machine with Docker, running against =main=, builds
   the image and runs all sixteen S1 scenarios (catalog #1–#12 and #17–#20)
   over real SSH between two containers, with every scenario matching its
   declared expectation: nine pass, and seven (#5, #6, #7, #8, #10, #11,
   #18)
   fail-as-expected under =known_failure=.
2. =make check= passes unchanged on a machine with no Docker daemon, with
   both coverage thresholds computed exactly as before — the =tests/e2e/=
   exclusion applied in both the Makefile =coverage= target and the CI
   coverage job.
3. =cargo test --all-targets= compiles every scenario and the harness
   without Docker and executes none of them.
4. Each S1 scenario is a straight-line function using only section 2.3
   vocabulary — no raw =docker= or shell strings in any scenario body, no
   fixed sleeps anywhere in harness or scenarios — and the harness contains
   no primitive that no S1 scenario exercises (the slice policy of
   section 7).
5. A deliberately failing scenario's output alone contains both trees, both
   statuses, the transcript tail, and both containers' logs; a failure
   raised inside the responder (=protocol serve=) is diagnosable from the
   same output via the responder's stderr log.
6. After a full run, and after a run interrupted by a panicking scenario,
   =docker ps -a=, =docker network ls=, and =docker volume ls= show nothing
   labeled =flocal-e2e=1=; a stale labeled object from a killed run is
   removed by the next =make e2e=.
7. A warm =make e2e= run (image cached) completes in under ten minutes on a
   developer machine or persistent runner; a cold CI run, including the
   image build, completes in under twenty-five minutes on a standard
   GitHub-hosted runner.
8. The CI =e2e= job runs =make e2e= on the Linux runner and fails the build
   on any scenario failure.
9. The image build context contains only =Cargo.toml=, =Cargo.lock=,
   =src/=, and the two runtime scripts =tests/e2e/entrypoint.sh= and
   =tests/e2e/flocal-wrapper.sh= (readmitted by =.dockerignore=
   negations) — no =.git=, =target/=, or other repository content reaches
   any build layer.
10. =docker inspect= on a scenario's containers shows no published ports,
    and the single =docker run= call site contains no =-p=, =--publish=, or
    =--network host=.
11. Promoting an expected-fail scenario requires only removing its
    =known_failure= wrapper — no scenario-body edits — and the wrapper
    fails loudly, naming the required promotion, when its scenario starts
    passing.
12. A container whose harness process was SIGKILL'd disappears on its own —
    no sweep, no external actor — within the configured lifetime bound
    (=FLOCAL_E2E_CONTAINER_LIFETIME_SECONDS=, default one hour).

* 13. Alternatives considered

- *One VM (or two) instead of containers.* Real kernels and real clocks would
  additionally cover clock skew and kernel-version variation, but VM images,
  hypervisor availability on CI, multi-minute boot times, and snapshot
  management dwarf the harness itself. Containers give the properties the
  stories actually need — process, filesystem, and network isolation with
  real SSH — at interactive speed.
- *Two processes plus network namespaces, no Docker.* Closest to zero new
  dependencies, but creating veth pairs and namespaces requires root or
  =CAP_NET_ADMIN=, hand-rolls exactly the lifecycle/cleanup/DNS work Docker
  provides, and still would not exercise a real =sshd= login environment
  without further assembly. Worth remembering if Docker ever becomes
  unavailable in CI; not worth building first.
- *Mocking the SSH transport.* Already exists (=tests/ssh_sync.rs=) and
  stays. It cannot validate the discovery probe against a real login shell,
  key authentication, =sshd= environment/PATH behavior, network loss, or two
  genuinely separate filesystems — the exact gap this feature closes.
- *docker compose.* A YAML topology file plus a second tool version to pin,
  in exchange for less runtime control than the harness needs (per-scenario
  networks, mid-scenario disconnects, per-run names). The harness issues the
  handful of docker commands itself.
- *testcontainers / bollard crates.* Rejected on dependency fit (section
  5.2).

* 14. Unresolved decisions

The decisions below remain recorded; where one asked for sign-off it still
does. The first slice this document describes is now /implemented/ —
=tests/e2e/=, =make e2e=, and the CI =e2e= job — with its findings recorded
inline throughout this document (the implemented public surface, the dump
contract, the three =main= bugs the harness newly discovered). The harness
landed with /zero/ product-code changes; the two product changes below
remain sequenced after it, and each proves itself by promoting
expected-fail scenarios (section 2.4).

1. *The =FLOCAL_WATCH_RESCAN_SECONDS= hook* — a product-code change (a few
   lines in =src/main.rs=, following the established =FLOCAL_*= pattern,
   with the clamped one-second floor of section 6). It is not needed for S1
   at all — the watch scenarios are later slice — so it sequences after the
   harness in any case. Approve the hook for the watch slice, or defer it
   and drop the watch scenarios (#13–#14) from the plan? Recommendation:
   approve with the clamp — the default is unchanged, environment variables
   are same-privilege configuration so production posture is not eroded, and
   the clamp removes the only misuse (a zero-interval hot loop).
2. *The =bound_peer= error-contract fix* — a product-code change to sign
   off, sequenced /after/ the harness: scenario #10 lands expected-fail,
   pinning today's behavior, and the fix ships as its own small pull request
   whose proof is #10's promotion. =State::bound_peer= (=src/state.rs:532=)
   calls =query_row= without =.optional()=, so a responder holding no
   registration for the share — exactly the state =reset_state()= creates —
   dies on =QueryReturnedNoRows= /before writing any protocol frame/; the
   connector observes a bare EOF ("failed to fill whole buffer"), never the
   designed rejection. Making a missing row return =Ok(None)= lets the
   existing graceful branch in =serve_io= answer, and the connector observes
   "remote rejected sync: peer identity mismatch" — the observable #10's
   final-form body asserts. This also fixes a real product error-contract
   hole that exists today: an internal database error plus an opaque EOF
   where a clear rejection was designed. Recommendation: approve, validated
   by #10's promotion.
3. *CI gating.* Should the new =e2e= job be required for merge from day one,
   or advisory for a probation period while its flakiness record is
   established? Recommendation: required — every wait is condition-based and
   the isolation is per-scenario, so a red run should be treated as signal.
4. *Ordering — accepted direction, recorded here rather than open.* The
   harness lands first, off =main=, with zero product-code prerequisites;
   scenarios for known-broken behavior land as strict expected failures
   (section 2.4). PR #2 (=agent/tombstone-retention=, open) stays open and
   is re-validated by promoting #6, #8, and #11 when it lands after the
   harness — on =main= today those scenarios fail outright because the
   deletion resurrects, which is exactly what their wrappers pin. The
   =bound_peer= =.optional()= fix becomes its own small pull request
   promoting #10. Implementation finding: the first real runs pinned three
   /more/ scenarios to PR #2 than predicted — #5 (an offline rename's
   delete half is lost after one unreachable cycle), #7 (the deleting
   peer's own apply recreates deleted parent directories), and #18 (a kind
   transition fails the connector's sync with "File exists") — all verified
   broken on =main= and passing on a merged probe tree. PR #2 therefore
   promotes six scenarios (#5, #6, #7, #8, #11, #18); with #10's separate
   promotion by the =bound_peer= fix, all seven wrapped scenarios are
   accounted for. Accepted trade-off: the tombstone data-loss fix merges
   later than it otherwise would; that is acceptable for the current
   single-user alpha, and PR #2's own unit-level regression tests already
   demonstrate fail-on-main at that level. The status-schema pin follows the
   same order (section 2.3): schema 1 at harness landing, bumped to 2 by the
   tombstone pull request together with the promotions.
5. *The slice boundary — expanded in review and recorded.* User review of
   this design asked for more scenarios in the first slice; #12 (ignore
   rules) and #17 (=.git= exclusion) moved into S1, and #18 (file/directory
   transitions), #19 (concurrent-delete convergence), and #20 (exec-bit
   round-trip and binary content) were added to it — none needs a product
   change. S1 is now catalog #1–#12 plus #17–#20, sixteen scenarios. The
   only remaining deferrals are the watch pair #13–#14, blocked on the
   section 14.1 hook, and #15–#16, blocked on their named vocabulary
   extensions (a kill-mid-transfer primitive; per-peer =Config= knobs).
6. *Rootless Docker and podman.* Every operation used works under rootless
   Docker; podman's CLI compatibility likely suffices. Is either a
   /supported/ configuration (tested, documented) or best-effort?
   Recommendation: rootful and rootless Docker supported; podman
   best-effort, undocumented.
7. *Base-image digest cadence.* Pinned digests need periodic bumps for
   security updates. Recommendation: manual bumps whenever the Dockerfile is
   touched; no automation until the repository adopts dependency-update
   automation generally.
8. *Parallel scenarios.* Serial in S1. Adopt parallel execution later only
   if wall-clock time becomes a real constraint; the per-run naming scheme
   already permits it.
9. *More than two peers — recorded expectation, not a current work item.*
   Raised in review: multi-peer support is an expected future requirement of
   the product, and the harness must not box it out. Section 3.1 names what
   stays flexible (per-peer handles, an N-container network, =peer-N=
   naming, an N-ary =containers()= growth path) and the one v0.0.1-shaped
   piece (the =Connector=/=Peer= split) that gets revisited when the
   product's topology grows. No current scenario exercises more than two
   peers.

* Update 2026-07-22: the watch slice and the section 14.1 hook

The watch slice landed (=agent/watch-rescan-hook=), closing unresolved
decision 1 in favor of the recommendation: approve the hook. As of this
update:

- *The =FLOCAL_WATCH_RESCAN_SECONDS= hook exists* exactly as section 6
  specified: =watch= reads it with a default of 30, and zero or an
  unparseable value falls back to the default — the deliberate deviation
  from the unclamped =FLOCAL_MAX_*= siblings, because a zero interval would
  hot-loop full rescans and connection attempts. The interval is parsed
  once at watch startup (=watch_rescan_interval= in =src/main.rs=, unit
  tested) and threaded into =watch_loop= as a parameter, keeping the loop
  deterministic in tests.
  - *Clarification of the section 6 / 14.1 "clamp" wording.* Those sections
    describe the sub-one-second guard as "a clamped floor of one second."
    The implemented — and intended — mechanism is /reject-to-default/, not
    floor-clamp: zero maps to the 30-second default, not to one second (a
    literal clamp would honor a one-second rescan for a =0= input). Because
    the value is whole seconds, the smallest interval an explicit config can
    select is therefore one second, which is the sense in which section 6's
    "one-second floor" holds. This supersedes the "clamp"/"floor" phrasing
    in sections 6 and 14.1 wherever the two readings would differ.
- *Catalog #13 and #14 are implemented* in
  =tests/e2e/scenarios/watching.rs=, both running the watcher at the
  one-second floor. #13 mirrors example 2.2.4 (its trailing comment
  clarified to match the actual early-return control flow: a failed
  =wait_for_file= returns before =stop()=, so =Watch='s Drop tears the
  watcher down). #14 takes the peer
  offline under a running watcher, edits and deletes on the connector,
  reconnects, and asserts the unattended catch-up through =wait_*=
  primitives (bracketed by an initial-sync precondition and a final
  tree-equality check) — no observing verb over the watcher's stderr, as
  its catalog row promised. The suite is now eighteen scenarios; the
  remaining "later" rows are #15–#16, still blocked on their named
  vocabulary extensions.
- *The reserved watch vocabulary arrived with its scenarios*, per the slice
  policy: =pair_with(Config)= (currently one knob, =watch_rescan_seconds=,
  applied to the connector's =watch= invocations), =watch_start()= /
  =watch.stop()=, and the =wait_for_file= / =wait_absent= twins of the
  existing assertion Conditions. =wait_status= remains reserved on paper
  with no home scenario — so section 7's bidirectional-vocabulary check,
  which grouped all three wait primitives under #13–#14, now holds only for
  =wait_for_file= and =wait_absent=; =wait_status= waits for a scenario that
  reads status eventually. The =mod.rs= re-export surface of section 8 grew
  from four names to six (=pair_with= and =Config=; =Watch= stays reachable
  only by inference).
- *=watch_start()= mechanics.* =docker exec -d= runs a constant
  =sh -c= start command that records the shell's pid and =exec=s =flocal
  watch=, so the recorded pid is the watcher's own (the =flocal= wrapper
  also =exec=s). The rescan knob travels as an environment variable on that
  exec. Start-up is verified — the primitive fails, with the dump, if the
  watcher dies before or during the wait for its pid. =stop()= signals the
  recorded pid inside the container per section 2.3 and additionally fails
  if the watcher had already died, so an unnoticed mid-scenario watcher
  death cannot pass. Every real signal (=stop='s SIGTERM, =Drop='s SIGKILL
  backstop) is gated on a =/proc/<pid>/cmdline= identity check, not a bare
  =kill -0=: the recorded pid can outlive the watcher and be recycled (the
  container caps pids), and the check makes it impossible to signal a
  process that merely reused the pid. Signals go through the shell's =kill=
  builtin (the slim image ships no standalone =kill=), with the pid as a
  positional argument, preserving section 9's no-interpolation rule. The watcher's
  stderr reaches the failure dump through the existing wrapper tee; its
  stdout under =-d= is discarded.

* Update 2026-08-20: multi-share scheduling acceptance

Six ordinary scenarios in =tests/e2e/scenarios/multi_share.rs= exercise the
installation scheduler through public commands, real processes, and real SSH.
The two original reproductions retain their success-path assertions without an
expected-failure wrapper: =sync add --yes= waits behind an active sibling and
completes its initial plan, while a confirmed =sync start= returns promptly,
is visible as durably enabled and queued, names the active root rather than an
internal ID, and converges after release.

Four focused scenarios extend that boundary:

1. =sync stop= removes a queued managed start before the active owner releases,
   and a later completed permit proves the canceled payload cannot run.
2. A second watch event becomes pending while round one still owns the
   installation.  After release, the older sibling request reaches a real
   apply stop while list/status show the persistent watch queued behind that
   sibling root; only then does the watch complete round two.
3. SIGKILL of the daemon discards request liveness but preserves enabled intent;
   restart reconstructs the still-queued managed start before release.
4. Two connectors on opposite relationship directions each commit their local
   managed request, then their daemon processes stop before either worker can
   submit a proxy to the peer.  Direct status proves both requests are durable
   at that barrier.  An unrelated maintenance request holds the higher-ID
   connector's remote installation past the former reservation lease.  After
   both daemons resume, status exposes the queued local or peer scheduling wait,
   the holder releases, and both relationships converge without a manual retry.

The harness retains one fixed sibling root.  The setup scenario uses the
=.e2e-global-contention-observed= hook when enqueue commits behind a live active
row or final OS-lock acquisition reports =WouldBlock=, because the relationship
is not yet configured and therefore cannot appear in =sync list=.  After
release it also asserts the command's captured human path and queue position.
Configured-share scenarios assert scheduling through list/status instead.
Default production builds contain no marker behavior.

The opposite-direction scenario uses a hidden, E2E-only protocol command to
hold an unrelated real maintenance permit.  Its RAII guard resumes the stopped
holder on success or unwinding.  The command is absent from ordinary builds and
does not bypass the scheduler.

The opposite-direction scenario also uses the E2E-only
=.e2e-stop-before-reservation= marker.  The worker reaches it only after
=sync start= has committed the request and returned.  =SIGSTOP= pauses the
whole daemon, which prevents any peer submission; the harness therefore reads
durable scheduling through =status= rather than the paused daemon's =sync
list=, validates both stopped process identities, and resumes both before the
apply-boundary assertion.

Target =sync start= commands run through the container's five-second =timeout=
with a one-second forced-kill backstop.  Setup and convergence retain the
normal thirty-second harness deadline.  Exit 124 or 137 is classified before
stderr, and container teardown remains the final process/network cleanup
backstop.  The specialized diagnostic-matching expected-failure helper was
removed after promotion; the general bug-first =known_failure= primitive
remains available for unrelated future reproductions.

The harness pins =sync list --json= schema 3 and =status --json= schema 6.  Its
schema-3 fields distinguish connection state from =idle=/=queued=/=active=
scheduling, identify local versus peer waiting, preserve byte-valued blocking
and active roots, identify both operations, and support the human
root-path/no-internal-ID assertion.
