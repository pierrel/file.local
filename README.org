#+title: file.local

=file.local= is a local-first, peer-to-peer directory synchronizer. The command
is named =flocal=.

* Build and try the alpha

Rust stable is required on both peers. Before upgrading an existing
installation to this version, verify that every registered share path is the
intended mounted directory on that machine. The installer records each legacy
root's filesystem device and inode as its durable identity. A missing,
symlinked, or later replaced root is rejected rather than being mistaken for
an empty tree and propagating mass deletions.

Run installation with the account's normal =HOME=, not an overridden home
directory. The installer verifies it against the systemd user manager on Linux
and the account directory on macOS before it can stop or rewrite the single
per-user service.

#+begin_src sh
make install
#+end_src

Managed sync needs a systemd user manager on Linux. On macOS, run the command
from a graphical login so it can install the per-user LaunchAgent; a headless
run installs the binary, retains =upgrade.pending= so ordinary commands cannot
migrate state, and asks you to run =make install= again from a graphical
session before it migrates state or resumes managed synchronization.

Run that command from a checkout of this repository on *both* peers. Ensure
=~/.local/bin= is in =PATH= and that non-interactive SSH can run =flocal= on
the remote peer. Pairing also checks =~/.local/bin/flocal= directly, since
non-interactive SSH sessions often use a smaller =PATH=. The remote directory
does not need to be initialized separately: pairing creates it when needed and
registers it under the initiating peer's share identity.

** Upgrade an existing installation

Use the same command for installation and upgrade:

#+begin_src sh
make install
#+end_src

For the first upgrade to the compatible installer, upgrade a relationship's
connector before its responder. The installer stages the complete candidate,
stops the managed daemon, waits for its idle or in-progress managed sessions to
end safely, migrates state, replaces the service definition, and starts every
enabled sync again. Pairing, enabled intent, pending recovery, and synchronized
directories are retained. Later compatible upgrades can also ask an inbound
responder session to drain itself, so endpoint order is no longer significant.

Foreground =flocal watch PATH= and one-shot =flocal sync PATH= are not owned by
the managed daemon. End all of them before the first upgrade from the previous
alpha. The previous binary releases its session lock while an initial plan is
waiting for confirmation, so that particular idle prompt cannot be detected by
the candidate. Active sessions are detected: the installer reports the
affected human-readable root while it waits, then leaves the old executable and
state unchanged, restores only a service that was running, and tells you what
to stop before retrying. Once this version is installed, a foreground watch
keeps its lifetime lock during later upgrades and receives the same safe
refusal. A responder-first immediate upgrade can also refuse while an old
inbound session is active.

An upgrade interrupted after publication but before managed migration and
service-asset publication finish leaves an owner-only =upgrade.pending= marker
that blocks ordinary commands from opening or migrating state. A headless
macOS binary-only install retains the same marker. Once those durable managed
phases finish, the installer removes the marker before starting the daemon; a
start or readiness failure leaves the fully migrated candidate stopped and
reports the same =make install= retry guidance. Do not delete a retained marker
or copy an older executable over the installed candidate; downgrades are not
supported.

If an older foreground =flocal watch PATH= was interrupted while applying a
change, install the candidate on both endpoints and then rerun =flocal watch
PATH=. The durable install intent recovers that interrupted apply. Do not
delete state, remove the intent, or pair the directories again.

Then, on one peer only, pair an existing local directory with an absolute
remote path:

#+begin_src sh
flocal sync add ~/src/example --host buildbox --remote-path /srv/work/example
#+end_src

The =--host= value can be a hostname, address, or =~/.ssh/config= alias.
=sync add= reports when it is scanning local files, waiting for the remote
file scan, and comparing the two file lists while it builds the first plan. It then
asks before changing file content in either directory. Pairing may create the
missing remote root directory first. After that confirmed initial
synchronization succeeds, it reports the connection and starts the initiating
peer's managed watch. The responder accepts incoming sessions but cannot
initiate them. Inspect or control local syncs with:

#+begin_src sh
flocal sync list
flocal sync stop ~/src/example
flocal sync start ~/src/example
#+end_src

=sync list= reports connection state separately from installation scheduling.
Connection state remains =stopped= (disabled), =starting=, =watching=,
=reconnecting=, =stopping=, or =blocked=; scheduling is =idle=, =queued=, or
=active=. A confirmed =sync start= may return successfully while its worker is
queued behind another share. It then runs automatically without another
command. =sync stop= cancels a queued managed start, and a daemon restart
reconstructs an enabled queued start from durable intent.

Human queue feedback names a blocking local share by its configured root, not
its internal ID:

#+begin_example
Waiting for /Users/alice/projects/notes sync to finish (queue position 1)
Synchronization slot acquired for /Users/alice/projects/work
#+end_example

When the wait is on the other installation, output deliberately stays generic:

#+begin_example
Waiting for the peer to finish another synchronization (queue position 1)
#+end_example

A broken local root, including a rename, deletion, replacement, or symlink, is
=blocked= with its reason and is not adopted automatically. Restore the
original directory and run =sync start --share SHARE= to retry it; =sync stop
--share SHARE= works even while its old path is gone. =sync list= also shows
the durable enabled setting separately from connection and scheduling state.

** Relationship lifecycle

Clean relationship removal uses this command:

#+begin_src sh
flocal sync remove [PATH | --share SHARE] [--local-only] [--yes]
#+end_src

Normal removal runs on the connector. It stops that relationship's worker,
asks the responder to detach the same relationship, then detaches locally. On a
responder, the command identifies the connector on which to run it. An exact
root path selects an available root; =--share= remains available when that root
is missing or replaced.

The command previews the root, share, known peer, and scope. Confirmation
defaults to no. Declining, entering an empty answer, or reaching end of input
prints =Relationship unchanged=, exits successfully, and changes nothing.
=--yes= skips the prompt but never the preview or a local-only warning. An
already-unpaired root is a successful no-op without a prompt.

A failed normal removal remains disabled and visible as =removing=; retry the
same =sync remove= command after correcting the reported error. Removal never
falls back automatically. =--local-only= is the explicit escape hatch on either
endpoint when the other endpoint is permanently unavailable. It warns that the
other endpoint may still retain the relationship.

Removal itself does not modify synchronized files. It retains the root and
share registration, root identity, recovery budget, conflicts, and recovery
objects. Any already-committed install recovery finishes before detach, so the
preview warns that visible paths may still be repaired first. Path-based
recovery commands still require an unavailable root to be restored.

New pairing first records a durable relationship ID before changing the remote
endpoint. A lost registration reply is shown as =registering=; retry =sync add=
with the exact same target and it reuses that ID. A different target is
rejected. If reachable, recover by retrying the add and then using normal
removal. Local-only abandonment warns that the responder may already be
registered and must also be detached locally before that root is reused.
Re-pairing an unpaired root creates a fresh relationship and initial union
plan. When pairing in the reverse direction, the retained root and conflicts
may be atomically remapped to the incoming share ID; =sync list= or =status
PATH= reports that new ID and the old =--share= selector no longer applies.

The =sync list --json= schema is 3. In addition to =role=,
=registration_pending=, and =removal_pending=, each entry has
=connection_state= and the scheduling fields =scheduling=, =waiting_on=,
=operation=, =queue_position=, =waiting_root=, =active_share=, =active_root=, and
=active_operation=. Root paths use the byte-preserving base64 path shape;
human output alone renders bounded escaped path labels. Human output adds
=disabled registering= and =disabled removing=; unpaired roots are omitted.
The =status --json= schema is 6 and adds the same scheduling object for the
selected share to the bound peer, relationship state, pending removal, and
removal error. Human status reports =registering=, =connector=, =responder=,
=removing=, or =unpaired= and always includes recovery, pending install, and
current queue state. Unlike list, =status PATH= shows a retained unpaired root
as not configured.

** Read-only client status

=flocal status --list --json= is the versioned, read-only status interface for
editor integrations and future clients. It never starts a daemon. When the
daemon is reachable it reports =source: live=; otherwise it reads only durable
state and reports enabled shares as =unknown=. Roots remain base64-encoded
native path bytes. The initial schema is 1 and deliberately contains only the
share identity/root, enabled state, connection and scheduling state, role,
initial-completion state, bounded diagnostic, and unsettled count.

** Emacs guard

[[file:emacs/README.org][flocal-guard]] is an optional Emacs 28+ companion,
tested with Eldev. Enable its global mode after installing =flocal=:

#+begin_src emacs-lisp
(require 'flocal-guard)
(flocal-guard-mode 1)
#+end_src

It discovers enabled shares that are not stopped through the read-only status
interface. Its modeline and =M-x flocal-guard-status= distinguish live from
stored status. A modified guarded buffer never saves on a cold or expired
status cache. When disk bytes differ from the visiting buffer's recorded
serialized-content baseline, it opens Ediff with the user buffer first and a read-only =DISK:=
snapshot second. Ediff's write-A saves the resolved user buffer only if disk
has not changed again; abort leaves both versions intact. This is accidental
clobber protection, not a filesystem compare-and-swap guarantee.

** Troubleshooting a managed watch

Start with =flocal sync list=. A healthy connector is =watching=;
=reconnecting= means it is connecting or retrying the watch session; and
=blocked= includes the reason the watch needs attention. =queued= is healthy
installation scheduling, not a connection failure, and does not advance the
transport retry count. =starting= and =stopping= are transitional; =stopped=
means the watch is disabled. A broken local root is one =blocked= case;
restore it and start the share again.

On Linux, the daemon is a systemd user service. Check its state, inspect the
current-boot logs, or follow new lines with:

#+begin_src sh
systemctl --user status flocal-daemon.service
journalctl --user -u flocal-daemon.service -b -n 200 --no-pager -o short-iso
journalctl --user -u flocal-daemon.service -f -o short-iso
#+end_src

On macOS, inspect the LaunchAgent with:

#+begin_src sh
launchctl print gui/$(id -u)/local.file-local.flocal-daemon
#+end_src

=flocal= does not currently route LaunchAgent stdout/stderr to a retained
macOS log. For live diagnostics, first stop the managed watch, run the watch
in a terminal, then start it again when finished:

#+begin_src sh
flocal sync stop PATH
flocal watch PATH
flocal sync start PATH
#+end_src

Linux watch lines in the journal, and foreground macOS watch lines, have a UTC
timestamp, for example
=Peer connected=, =Peer connection lost; retrying=, =synchronization failed;
retrying in background: ...=, or =synchronization resumed after N failed
attempts=. File actions such as =UPLOAD=, =DOWNLOAD=, and =DELETE= appear only
after both peers apply them. When asking for help, include =flocal sync list=
and the recent Linux journal or macOS foreground-watch lines from both peers.

The current code is proof-stage alpha software: review the explicit implementation gaps in
[[file:docs/2026-08-13-v0.0.1-design-reconciliation.org][the current design reconciliation]] before using it on irreplaceable data. The
dated [[file:docs/2026-07-14-alpha-implementation.org][alpha implementation state]] preserves the implementation history.

It follows the local-first principle that the copy on your device is primary:
files remain ordinary local files, every peer can read and change them without
a network connection, and synchronization happens when peers can reach each
other. There is no authoritative server. This project is directly inspired by
Ink & Switch's foundational [[https://www.inkandswitch.com/local-first-software/][Local-first software]] essay and its ideals of offline
work, multi-device access, longevity, privacy, and user control. Their
[[https://www.inkandswitch.com/pushpin/][PushPin]] report explores the production peer-to-peer synchronization problems
that this smaller project will meet in practice. The detailed research behind
the initial design is in [[file:references/][references/]].

* Design

Version 0.0.1 synchronizes one directory between two equal Linux or macOS
peers. The connector reaches the other peer using an ordinary SSH hostname,
address, or =~/.ssh/config= alias. SSH is only the first transport: WireGuard,
a LAN, or the public internet may provide connectivity underneath it.

While connected, both peer processes watch regular files, directories, and
symbolic links. Edits made while a watcher is absent remain ordinary safe local
files and are discovered by the next reconciliation scan. Git-compatible
=.gitignore= rules leave ignored paths entirely local, and =.git= is always
excluded. Names beginning =.flocal-tmp-= are reserved for crash-recovery
temporaries and are never synchronized. Only Git-portable metadata, file
contents, symbolic-link targets, and the executable bit synchronize.

Excluding =.git= means the working trees converge, but Git state does not:
branches, =HEAD=, the index, commits, and staged changes remain independent. The
supported v0.0.1 workflow assigns Git control to one peer at a time. The other
peer may edit files, but does not commit, stage, or switch branches until the
working trees are synchronized and Git control is deliberately handed over.
Both clones use an ordinary Git remote to transfer commits. This handoff is
entirely user-managed and =flocal= cannot verify it. Automatic Git-state handoff
is outside v0.0.1; =flocal= never reads or runs Git commands implicitly.

Concurrent text edits use a three-way merge from the last shared version.
Non-overlapping line changes merge automatically. When both sides change the
same hunk, the later change wins that hunk. When an overlap or fallback creates
a recovery conflict, both peer inputs, plus the base and merged result when they
exist, are retained. =flocal status= reports the per-share recovery charge and
physical bytes reclaimable now. =flocal conflicts prune= previews a token-bound
selection before deleting local recovery records, and =flocal conflicts budget=
can only raise the durable local or peer allowance. A sync that would exceed a
recovery limit stops before visible mutation instead of retrying forever.
Binary files and files without a common base use the same last-write-wins rule
for the whole file. Deletes and unambiguously paired observed renames
participate in the same ordering. An ambiguous rename event, including one that
macOS reports without an old/new pair or one discovered only by a later scan,
falls back to path-wise delete-plus-create and is reported rather than guessed.
Ordinary transfers stream files larger than memory. Text merging is bounded to
256 KiB and 4,096 lines per input; larger or non-text files still synchronize
through recoverable whole-file selection.

=flocal-daemon= keeps one SSH protocol session open for every enabled connector
share and observes both peers. =make install= installs the normal =flocal=
binary plus one per-user service: a systemd user service on Linux and a
LaunchAgent in a macOS graphical session. It restores enabled watches after
login or daemon restart; =sync start= also asks the installed service manager
to start the daemon if necessary. =sync stop= disables only that share.

Every installation-wide mutation enters one persisted FIFO scheduler before
acquiring the existing global OS lock. Requests carry owner-only liveness
files, so a crashed process cannot leave a permanent queue head. A persistent
watch rejoins the tail after every round; it cannot retain ownership and starve
an older request for another share. Managed enablement and queue insertion are
one durable operation, while managed stop disables the generation and cancels
its queued request atomically.

A network round reserves the scheduler on both peers before either side starts
mutation. The installation with the lower peer ID assigns the shared order,
independent of connector direction, and both endpoints prepare and commit that
reservation before taking their OS permits. This prevents simultaneous
opposite-direction relationships from each holding one installation while
waiting for the other. Peer queue progress carries only a coarse position and
never exposes an unrelated remote path or share ID.

A local or
remote filesystem event schedules synchronization after a 250-millisecond
debounce, capped at two seconds during a continuous burst. Change-driven rounds
still perform a complete reconciliation scan in this alpha; incremental
dirty-path scanning and operation deltas remain deferred. While healthy and
idle, peers exchange a small heartbeat every 30 seconds. A full safety audit
runs every 15 minutes on the same session to bound silently missed filesystem
notifications without returning to frequent SSH and scan polling.

On startup and after sleep, network loss, or daemon restart, both peers scan
before the session reports connected. The connector retries temporary failures
with bounded backoff and synchronizes unattended when connectivity returns. In
daemon logs, path actions are recorded only after both peers successfully
apply them. The first failed attempt is reported immediately, continuing
failures are summarized every five minutes without log flooding, and recovery
reports how many attempts failed. Explicit =flocal sync= output remains a
proposed plan because it may precede initial confirmation.

Startup waits up to five minutes for the peer's first response. Each
synchronization round carries a five-minute elapsed budget checked between
synchronous filesystem operations. Protocol reads use the time remaining in
the applicable startup or round budget. Once a frame starts, its remaining
prefix and payload still have a hard 30-second deadline. This lets an
interrupted install recover without a reconnect loop while keeping partial
frames and silent peers bounded.

If a file changes after a round scans it but before installation, watch keeps
that local change, records the path as =UNSETTLED=, and recalculates immediately
without reconnecting. A path that changes again is isolated so stable sibling
paths can finish. A later full round reports =SETTLED=. =flocal status= and
=sync list= expose durable unsettled state across daemon restarts.

Persistent watch uses protocol version 7, so install or upgrade =flocal= on both
peers before adding a managed sync. Explicit =flocal sync= uses protocol
version 6. A persistent protocol mismatch keeps the
worker reconnecting with bounded upgrade reports until both peers support
version 7; it never silently falls back to polling. Downgrading does not change
synchronized state, though persistent watch remains unavailable until both
peers support version 7.

Relationship registration and removal capabilities each start at
version 1 on the separate fixed =flocal protocol relationship= entrypoint.
Both synchronization modes use =flocal protocol serve=. Both peers must be
upgraded before a new relationship
can be added or removed. An existing legacy relationship continues to sync;
the legacy registration message cannot create or rebind a relationship.

* Stories

** v0.0.1-alpha - proves the synchronization model

- Two equal peers synchronize in both directions over SSH.
- Local work continues offline and synchronizes after reconnection.
- Initial scan, filesystem watching, dry-run, status, ignore rules, atomic
  writes, tombstones, and recoverable last-write-wins conflicts work.
- The connector runs an enabled sync through one per-user =flocal-daemon=.
- Concurrent text edits with a shared base use deterministic three-way merge;
  other conflicts retain recoverable whole-file inputs.

** v0.0.1 - works for me

- Linux systems with a systemd user manager and macOS graphical sessions install
  one per-user daemon, so normal use does not require managing a foreground
  process.
- Saving a buffer in Emacs is noticed promptly, including editors that save by
  writing a temporary file and renaming it over the original.
- A local editor and a coding agent working from the remote copy can alternate
  or work offline without treating either machine as authoritative.
- Three-way text merge preserves non-overlapping changes and applies
  last-write-wins only to overlapping hunks.
- The service reconnects and catches up without intervention when either peer
  or its network returns.

** v0.1.0 - works for my family

The next milestone will define invitations, more than two peers, refined
service-management UX, and recovery retention suitable for non-technical users.

** v1.0.0 - works for another community

The stable milestone will be defined from experience running the earlier
versions across real directories and peers.
