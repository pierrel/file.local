#+title: file.local roadmap

This roadmap records the minimum product work needed to move beyond the alpha,
followed by deliberately deferred work. The alpha exit is a focused =v0.0.1=:
two peers should support Pierre's everyday macOS/Linux editor-and-agent workflow
without data loss or manual repair of synchronization state.

* Exit alpha: =v0.0.1=

The existing two-peer synchronization, managed daemon, offline catch-up,
whole-file conflict recovery, and automatic stale-install recovery are the
foundation. Leaving alpha requires one substantial synchronization feature and
the lifecycle and safety work that makes it trustworthy.

** DONE Reconcile the durable design with the implementation

Update the dated design and implementation state before changing the merge
model. Remove stale descriptions of already implemented background services and
recovery behavior, distinguish the current alpha from the intended =v0.0.1=,
and make the remaining acceptance criteria explicit.

** DONE Deterministic three-way text merge

When both peers change a text file from the same retained base, preserve
identical and non-overlapping edits from both peers. Resolve only overlapping
hunks by the existing deterministic last-write-wins ordering, without placing
conflict markers in the working file.

This includes the state model needed to make merging and recovery real:

1. Retain and identify a common base until it is no longer needed.
2. Produce one merged operation that causally descends from both inputs.
3. When overlap or fallback creates a recovery conflict, store the base when
   available, both inputs, merged result when available, ordering, and any
   overlapping hunks.
4. Restore any version retained by that recovery conflict.
5. Fall back to whole-file last-write-wins for binary, oversized, or baseless
   files while retaining both available inputs.
6. Retain the recoverable input for destructive delete-versus-edit and
   incompatible path-kind conflicts.

Text classification and merging must use bounded memory and CPU. Any spill
storage is owner-only and counts toward the existing state budget; a hostile or
pathological peer input must not turn merging into unbounded work.

Live collaborative editing, CRDTs, and semantic language-aware merging are out
of scope.

** DONE Bound recovery storage

Add explicit conflict pruning with a preview. Never prune a base still required
for a future merge. Report recovery-object disk usage in status so a user can
act before the configured state budget safely stops synchronization. Add a
durable per-share command to raise that budget locally or on the peer. Budget
exhaustion and =ENOSPC= must stop before changing the visible file and clean up
any partial unreferenced object.

Automatic acknowledged-tombstone collection is not required to leave alpha;
tombstones may remain indefinitely in =v0.0.1= because that behavior is safe and
visible. It is required before a broader stable release.

** DONE Remove a synchronization relationship cleanly

Implement =flocal sync remove [PATH | --share SHARE] [--local-only] [--yes]= as
specified by the
[[file:docs/2026-08-17-clean-relationship-removal-design.org][implemented relationship-lifecycle design]]. Normal removal runs on the connector,
stops its worker, and detaches both endpoints. The responder directs the user
to the connector. Confirmation defaults to no; =--yes= skips only the prompt.
An explicit =--local-only= escape hatch works on either endpoint, always warns
about the remaining peer state, and is never an automatic fallback.

Failed registration and removal must remain disabled and visible as
=registering= or =removing= until the user retries the same command. Removal
must finish any committed install recovery first, never modify synchronized
files itself, and retain the root, identity, conflicts, recovery objects, and
budget for recovery or a fresh re-pair. Reverse-direction re-pairing may
atomically remap that retained state to the new share ID. Ship the list/status
schema bumps and the isolated relationship protocol with the implementation;
both peers must be upgraded for new pairing or removal. The implementation and
acceptance gates completed on 2026-08-17.

Uninstalling the global per-user daemon is not an alpha-exit requirement; it may
remain installed and idle when no sync is enabled.

** DONE Upgrade paired installations without rebuilding synchronization state

=make install= now owns one staged, locked upgrade from service stop through
candidate publication, transactional state migration, service replacement, and
managed restart. Idle and in-progress managed syncs retain their enabled intent
and recover automatically. A durable installation barrier drains compatible
long-lived sessions and prevents commands from opening SQLite during migration;
the immediate upgrade from an unaware binary also takes every legacy mutation
lock before replacement. Foreground commands and responder-first legacy
sessions receive a bounded, path-naming safe refusal rather than a partial
upgrade.

The E2E suite builds the pull request's exact base revision separately from the
candidate, creates a real paired installation with the base binaries, and
carries its working trees and state through the candidate. Ordinary scenarios
cover idle restart, an apply interrupted at the service stop, compatible
responder-first reinstall, foreground refusal and retry, and migration failure
and retry. CI checks out full history and pins that transition to the exact
pull-request base SHA. Downgrade and network-distributed updating remain out of
scope.

** TODO Schedule multiple shares without manual retries

Keep the single global synchronization owner that protects the installation's
shared database, recovery journals, and object store, but treat contention
between otherwise healthy shares as normal scheduling rather than an operator
error.  If one share is scanning, applying, or recovering, =sync start= for an
already confirmed second share must durably enable and queue it, then return
success.  The daemon must eventually run it after the current owner releases
the installation, without the command remaining alive or being repeated.  An
initial-incomplete share may wait for ownership, but must still show and confirm
its initial plan before becoming enabled.

Foreground =flocal watch= and one-shot =flocal sync= commands must wait with a
visible queued state and continue automatically instead of exiting with
“another synchronization operation already owns this installation.”  Such a
wait must remain cancellable, =sync stop= must cancel a queued managed start,
and a continually active share must not starve another queued share.

No two mutation rounds may run concurrently.  Queueing must remain distinct
from connecting, reconnecting, transport failure, recovery failure, and a
blocked invariant.  =sync list= must show the installation-wide active and
queued shares; =status= and watch output must show the selected share's state
and the active share it is waiting for.  Linux end-to-end tests must hold one
share inside a real round and prove both the durable =sync start= path and the
foreground-wait path continue without a repeated command.  They must observe
=sync start= return success while the first share still owns the installation,
then observe the managed start as durably enabled and queued before releasing
the first share.  They must preserve the initial-plan confirmation gate, cover
cancellation and repeated contention, then prove both shares converge.  The
native macOS-to-Linux safety gate must exercise the same multi-share
contention.  This is required for leaving alpha.

The Linux E2E suite now carries six ordinary acceptance scenarios for this
item.  The original =sync add= and confirmed =sync start= reproductions are
promoted to their success paths.  Four focused scenarios cover canceling a
queued managed start, allowing an older queued share to run between persistent
watch rounds, reconstructing an enabled queued start after a daemon crash, and
barrier-starting opposite-direction relationships while an unrelated installation
holder and typed scheduling state make their overlap deterministic.  This roadmap item remains
TODO until the complete validation gate, including the native macOS-to-Linux
workflow above, has passed.

** TODO Make operational state durable and visible

Persist and report the last successful synchronization, last connection
attempt, last complete scan, current retry state, last actionable connection
error, pending work, and whether remote state is unknown while offline. A stale
or unknown snapshot must never look like an authoritative zero-pending state.
This must remain useful when a managed macOS worker failed outside a foreground
=flocal watch= session and complement the recovery usage reported by status.

** TODO Preserve destination-local filesystem metadata

Continue synchronizing only the executable bit, but preserve the existing
destination file's owner, ordinary permission bits, ACLs, and extended
attributes across replacement. If the target cannot preserve its local
metadata, block the replacement instead of silently discarding it.

** TODO Give observed renames deterministic semantics

Capture a rename as one operation when the watcher supplies an unambiguous pair
or file identity, so concurrent rename, edit, or delete resolves by the same
deterministic ordering. Report any ambiguous rename, including an unpaired macOS
filesystem event or a later scan discovery, and fall back visibly to path-wise
delete plus create rather than guessing. An unobserved rename-and-edit remains
ambiguous in =v0.0.1= and does not require hidden identity metadata in user
files.

** TODO Complete the cross-platform safety gates

Before tagging =v0.0.1=:

1. Exercise native macOS-to-Linux synchronization over SSH through sleep/wake,
   network loss, offline edits on both peers, atomic editor saves, daemon
   restart, and upgrade.
2. Verify that every exact filename can round-trip on the target filesystem and
   detect case-folding and Unicode-normalization collisions before applying a
   tree that the target cannot represent safely.
3. Inject interruption at every durable install transition and prove restart
   yields the complete old file, the complete new file, or a recoverable
   recorded intent, never mixed or unexplained state.
4. Stress concurrent symlink replacement at filesystem boundaries.
5. Dogfood the native macOS/Linux workflow through repeated reconnects,
   conflicts, and upgrades with no manual metadata repair or lost recoverable
   version.

* After =v0.0.1=

These are intentionally not requirements for leaving alpha unless real usage
shows that one blocks the two-peer workflow.

** TODO Collect acknowledged tombstones

Remove a tombstone only after both peers have durably acknowledged it and no
retained merge base refers to the deleted version.

** TODO Replace full scans where measurement justifies it

The full scanner is the correctness backstop. Add incremental filesystem event
handling or transfer deltas only when measured tree size or transfer cost makes
the current behavior inadequate.

** TODO Make the peer-side =flocal= executable more discoverable

It currently:

1. Tries =command -v flocal=.
2. Falls back to =$HOME/.local/bin/flocal=.
3. Validates and stores the resulting absolute path.

Revisit this when supporting more installation layouts or more than two peers.

** TODO Broader product surface

More than two peers, invitations and discovery, guaranteed inference of
unobserved rename-and-edit operations, resumable chunk transfer, synchronization
of ACLs and extended attributes between peers, a GUI, and packaged installers
remain outside the =v0.0.1= exit bar. Destination-local ACLs and extended
attributes are nevertheless preserved during replacement.
